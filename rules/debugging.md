## Debugging via logs

Aiko writes a single, level-disciplined log stream that lands in three places at once: stderr (live console), `data/app.log` (rotating, 5 MB × 5 files), and an in-process ring buffer (last 1000 lines) exposed over MCP. Every line is shaped the same way — memorise the shape and the canonical fields and you can answer most "what just happened?" questions with one or two MCP calls.

### a. Where to look (priority order)

1. **`tail_logs(n=200, level="DEBUG", module_contains=…)`** — first stop. Instant, scoped, level-filterable. Use `module_contains="prompt"` to focus on `app.core.session.prompt_assembler`, `module_contains="ollama"` for the LLM client, etc.
2. **`read_log_file(lines=2000, grep="turn=abc12345")`** — when the issue is older than the ring (~1000 lines back) or you want to follow one turn end-to-end. Hits the rotating `data/app.log` (and its `.1`…`.5` siblings).
3. **`data/app.log` directly via Read tool** — for offline / cross-session forensic work, including reading rolled siblings.
4. **`terminals/*.txt`** — last resort for noise outside the `app.*` loggers (uvicorn, fastmcp, library warnings).

`get_log_config` returns the current effective configuration (level, file path, module overrides, ring usage).

**Frontend crashes are not in this stream.** They arrive over HTTP from the browser and are recorded separately — start at `get_ui_crashes()`, see §g.

**Nor are native crashes.** If the process *vanished* rather than logged an error, nothing in this stream will explain it — start at `get_native_crashes()`, see §h, and do not trust the Python frame in the `faulthandler` dump.

**One stream, one exception.** The P44 prompt-cache telemetry writes JSONL to `data/prompt-cache.jsonl` instead, through an `app.promptcache` logger with `propagate = False` — a per-turn record would bloat `app.log`, and its only consumer is a script. It is **off by default** (`logging.prompt_cache_log_enabled`); turn it on for a measuring session and read it back with `python scripts/prefix_break_report.py`. See [`docs/prompt-caching.md`](../docs/prompt-caching.md#measuring-where-the-prefix-breaks-p44).

### b. Standard line shape

Every record is formatted as:

```
[YYYY-MM-DD HH:MM:SS,mmm] LEVEL [logger.name turn=abc12345] message text key1=val1 key2=val2
```

`turn=…` is an 8-char hex correlation id allocated by `TurnRunner.run()` and propagated via a `contextvars.ContextVar` ([`app/core/infra/log_context.py`](../app/core/infra/log_context.py)). When no turn is active you'll see `turn=-`. The canonical structured fields (memorise these for precise greps):

- **Turn lifecycle**: `model=`, `ctx_pct=`, `prompt=`, `completion=`, `first_token_ms=`, `total_ms=`, `eval_ms=`, `tools=`, `compactions=`, `mood=`, `aborted=`, `chars=`, `filler=`.
- **Prompt assembly**: `ctx=`, `budget=`, `est_tokens=`, `sys=`, `hist=`, `user=`, `rag_tokens=`, `history_msgs_in=`, `history_msgs_out=`, `inner_blocks=`, `summary_active=`, `compaction=`, `aggressive=`.
- **Scheduler**: `jobs_run=`, `elapsed_ms=`, `queue_after=`, `idle=`, `names=`, `submitted=`, `ran=`, `cancelled=`, `windows_opened=`.
- **Ollama**: `msgs=`, `tools=`, `stream=`, `prompt_tokens=`, `completion_tokens=`, `tool_calls=`, `format_json=`, `stopped=`.
- **STT**: `chars=`, `duration_ms=`, `model=`, `language=`, `init_ms=`, `device=`, `sample_rate=`, `max_s=`, `silence_s=`.
- **TTS**: `voice=`, `provider=`, `init_ms=`, `chunk_chars=`, `speed=`, `generate_ms=`, `played_ms=`, `queue_depth=`, `drained_chunks=`.
- **Proactive**: `source=` (`prepared`|`llm`).

### c. Symptom → grep target

| Symptom | First check |
|---|---|
| **Aiko silent / no reply** | `tail_logs(level="DEBUG", module_contains="turn_runner")` → find the failed `turn=…`, look at `first_token_ms=` and surrounding ERROR lines. Then `read_log_file(grep="turn=<id>")` to grab everything correlated. |
| **The whole process died / "Aiko crashed" with nothing in the log** | `get_native_crashes()` — a native memory fault, not a Python error. Read `module` (the DLL owning the faulting address) and `duplicate_openmp`, **not** the Python frame in the `faulthandler` dump, which is an innocent bystander. §h. Rule out a hardware theory early: an access violation is a pointer bug, and memtest/OCCT passing tells you nothing about it. |
| **Voice mode never picks up** | `set_log_level("app.stt.realtime_stt_service", "DEBUG")`, then `tail_logs(module_contains="stt")`. Look for missing `STT engine ready:` INFO or repeated capture errors. |
| **TTS stutters / drops** | `tail_logs(module_contains="tts")`. Cross-reference `TTS enqueue:` / `TTS play done:` DEBUG with `tts state:` transitions in `app.tts_queue`. |
| **Wrong context retrieved** | `set_log_level("app.core.session.prompt_assembler", "DEBUG")`, replay the turn, then read the `prompt built:` line for `rag_tokens` / `providers` / `slowest_provider` / `history_msgs_in/out`. |
| **Memory not recorded** | `tail_logs(module_contains="memory")`, look for `memory:` INFO lines from `turn_runner`, confirm the extractor ran. |
| **A worker that "runs fine" has never actually produced anything** | Absence-shaped bugs do not appear in logs — a silent early return logs nothing, and the fact-checker sat at one web search in three months because `_maybe_enqueue_claims` got a dict where it expected a `Memory`. **Count rows, don't read logs.** For F1: `SELECT value FROM kv_meta WHERE key='fact_checker.queue'` (persistently `[]` with claim-bearing memories present is the tell), `fact_checker.rate_state` (`last_allow_at` months old = it has not searched), and `SELECT COUNT(1) FROM memories WHERE json_extract(metadata,'$.last_verified_at') IS NOT NULL` (zero = no verdict was ever applied). Then run [`scripts/fact_check_backfill.py`](../scripts/fact_check_backfill.py) to replay the stored corpus through the real gates and see what *should* have queued; its skip histogram names the gate responsible. The same shape applies to any hook-fed worker — `user_correction_worker` logging `no_candidates` on 1079 consecutive runs is the same class of signal. |
| **A worker runs on schedule and skips every single time** | The complement of the row above: here the worker *does* log, and the line reads like an idle beat. `rg -o "<name>-worker skip: [a-z_ ]+" data/app.log \| sort \| uniq -c` — a **100% skip rate with a single reason** is never a coincidence, and it separates "nothing to do" from "cannot do anything" in one command. The belief and promise workers sat at 44/44 and 88/88 `no recent turns` for months because they were wired with the bare `session_id` while `messages.session_id` holds the scoped `f"{user_id}:{session_id}"` (H19). **Any chat-db read must key on `session_key`, never `_session_id`.** Note the idle scheduler will not rescue you here: zero pressure from a broken demand probe still gets **heartbeat**-admitted, so a worker with an unreachable input runs forever and accomplishes nothing. Both workers now log at WARNING when their key matches no message at all. |
| **An LLM worker runs, burns 30+ s of GPU, and reports zero items** | Suspect the *answer budget* before the prompt. `rg -o "answer truncated: surface=\w+" data/app.log \| sort \| uniq -c` and `rg "thinking starved" data/app.log`: on a `think=True` call the hidden trace shares `num_predict` with the answer, and a trace of 1.6k–5.1k tokens against a 400-token answer budget returns `done_reason="length"` with **empty content**. The tell is that `completion_tokens` is identical to the token on every line for a given surface (`num_predict` + `think_num_predict_headroom`) — that is a budget wall, not model variance. 98 such calls across 10 surfaces, and the promise + belief workers persisted **nothing** for eight and ten weeks (H27). Two follow-ons. **(1) Read the failure reason, not the count.** `promises=0` must mean "the model answered, and the answer was empty"; if a worker collapses "no answer" into `[]`, every run reports success — the reasons are now distinct (`llm_empty_answer` vs `llm_unparseable` vs `llm_error`), and only the middle one is about parsing. **(2) `llm-unparseable` is only actionable with the payload.** Both workers logged the verdict and not the answer for months, which hid a plain schema mismatch: `format_json=True` returns an *object*, and both prompts asked for a bare array. Use [`app/llm/json_answers.py`](../app/llm/json_answers.py) (`parse_json_array_answer`) rather than a fresh `json.loads` — it accepts the object wrapper, a bare array, `{}` as "nothing found", a drifted key, and an array embedded in prose. Fixing a per-surface `think` flag is the wrong layer: the same symptom was patched at two call sites in June and was still live at ten in August. |
| **Fact-checker never verifies anything / verdicts look arbitrary** | Two different failures, and the log tells them apart. **No supply**: `rg -c "fact-check enqueued" data/app.log` returns 0 while `rg -o "enqueue skip: [a-z]+" data/app.log \| sort \| uniq -c` shows a single dominant reason — for `personal` that is usually *correct* (the memory-level name check is the only gate that knows a row is *about a person*; the token scrubber only removes the name, not the sensitive content, so do not "unblock" it). **Bad payload**: run `python scripts/fact_check_backfill.py --limit 5000 --json` and read the `sentence` beside each `text`. `text` is the search query and must stay narrow; `sentence` is the proposition the model adjudicates and must actually assert something. A claim reaching the model as a bare span (`"2026"`, `"The Rent"`) means the sentence was lost — F1 verified spans for months and 0 of 90 contained a verb (H20). A spurious `contradict` there is not harmless: `|delta| > 0.2` replaces `memory.content` outright. **The outbound query is a third failure with the same root**: a span scrubbed of names can be safe and still unusable (`'playful moments with Jacob'` → `'playful moments with'`). F6's reformulator now receives the sentence as `CONTEXT` alongside the span, so check `rg "query reformulated" data/app.log` — output byte-identical to the input on most lines means it is being called with nothing to work from (27 of 34 before this), and a query that gained a *guess* rather than a predicate (`Back Camp` → `Back Camp TV series`) is the signature of a span with no verb. Planner-authored queries pass `already_neutral=True` and skip the rewrite by design; the deterministic scrub still runs on them, and that scrub is the only leak guard, so never gate a search on anything else. |
| **iOS PWA: no TTS after locking/unlocking the screen, but the phone shows audio playing** | The context is a zombie — iOS reclaimed the audio unit while the app was backgrounded and `resume()` still resolves to `state === "running"`. Every guard reads healthy, so nothing is dropped and nothing is logged; the media indicator is the keep-alive loop, not speech. `AudioOutputManager.onForeground()` now **replaces the context after any background stint** rather than inspecting it (`[ui] audio contextReplaced` with `reason=foreground`); see [`docs/voice-mode.md`](../docs/voice-mode.md). If you see `audio dropSuspended`, that is the honest-suspend failure — it needs a user gesture, and the "Sound is off" readout plus one tap is the intended path. **Two traps that made this recur.** (1) The original fix probed `currentTime` and rebuilt only a *frozen* clock. iOS also hands back contexts whose clock advances while the output reaches nothing, and no page-readable signal separates that from health — the analyser sits before `destination` and reports the samples it feeds into a void. **Do not re-add a health check as the gate**; a live clock proves rendering, not audibility. (2) `logging.ui_log_categories` must contain `"audio"` or the endpoint drops every one of these lines *silently*; it was missing from `config/default.json`, so this whole row was ungreppable until 2026-08. Confirm the plumbing works before concluding "no logs" means "nothing happened". Settings → "Restart sound" calls `restart()`, which is the same unconditional replacement — it used to call `onForeground()`, a no-op on a context already reporting `running`, which is why force-quitting was the only cure. |
| **A pooled cue is armed constantly and never surfaces** | Read `cue_decisions` grouped by `reason`. `topic_miss`, `importance_floor`, `cadence_block`, `no_stock` and `cross_lane` come from the provider's own bail point ([`cue_accounting.py`](../app/core/proactive/cue_accounting.py)); `lost_priority:<cue>` and `question_balance` are attributed structurally. **`provider` is the catch-all and means the provider declined without saying why** — a table still dominated by it points at an uninstrumented bail rather than at a cause. When it does dominate, stop reading reasons and **read the payloads against the gate's own expression**: the L30 gap path gates on `float(payload.get("importance") or 0.0) >= 0.55`, and all 13 invented hypothesis cues carried no `importance` key at all while all 13 grounded ones did — a missing key is 0.0, so half the shelf was structurally unreachable rather than unlucky (H7). Any gate that coerces a missing field to a falsy default will read "absent" and "worst possible" identically. |
| **An always-on block is present every turn but nothing seems to respond to it** | It may be a constant. `turn_prompt_blocks` stores the rendered length per (turn, block), so `SELECT block, COUNT(DISTINCT assistant_message_id) n, COUNT(DISTINCT chars) d FROM turn_prompt_blocks GROUP BY block` finds every candidate at once: **`d = 1` over hundreds of turns means the block never changed**. Five such blocks are fixed grammars and are meant to be; the rest advertise themselves as learned. K13's `style_signal_block` sat at exactly 40 chars on 99.7% of 2018 turns, said one of three things ever, and changed four times in twelve weeks (H21). The cause is generic: **an absolute threshold applied to a stable trait is a constant, however well tuned** — three of its five axes had never emitted a label and could not (emoji bar 0.05 against a corpus maximum of 0.000, slang bar 0.15 against 0.009, question bar 0.40 against 0.333). For any "lately"/"currently" signal, check it compares against a baseline rather than a fixed number. Note `chars` is a *lower* bound on variation — equal lengths do not prove equal text — so it produces a shortlist to read the renderer for, not a verdict. |
| **A deviation / z-score signal fires on ~0% or ~100% of turns** | Two arithmetic mistakes, both of which produced a plausible-looking implementation. **Never fires**: you are dividing by the per-turn standard deviation when the tested quantity is a *mean of N samples* — the yardstick is the standard error `sd/sqrt(N)`. On a binary axis the per-turn spread is ~0.5 and no window mean is three of those from anything. **Always fires high for the first few months**: an EWMA seeded at 0.0 has a long cold start — at `alpha=1/300` it reaches only 49% of the true mean after 200 observations, so everything reads "above baseline". Floor the effective rate at `1/count` so it is an exact running mean until the decay horizon. Both bit K13 (H21) and both are covered by named regression tests in `tests/test_style_signal.py`. |
| **A prompt block never appears at all / "is this feature even alive?"** | The complement of the constant-block query, on the same table. `_PROMPT_BLOCK_TIERS` (`app/core/session/prompt_assembler.py`) is the declared inventory and `turn_prompt_blocks` is what reached the model, so the set difference is every block that has never emitted a character — 47 of 113 when this was first run. **Empty renders are dropped before the insert, so absent means "never rendered non-empty", not "never wired".** Two large decoys before you read anything into a name: (1) `grounding_line_mode == "replace"` deliberately zeroes ten T4/T5 ambient + affect blocks and fuses them into `grounding_block`, and (2) most T6 detectors (`rupture`, `boundary_clash`, `fact_reversal`, `user_correction`) *should* be silent over a short window — **rarity is the design intent for about half the list, so "never fired" is not evidence on its own.** The discriminator is never the block, it is the producer: read the worker's `idle_worker run done: <name> ... result={...}` payloads, which name their own skip reason. `candidates=6 ... drafted=0` on every run is a finding (H22); `no_finding` on a worker whose input is genuinely empty is not. |
| **A worker reports the same "new" item on every single run** | It is being created and then discarded before the save, and the bookkeeping is reading the pre-discard value. K73 logged `new=['saturday:afternoon:casual_check_in']` on eight consecutive sweeps because `merge_rituals` collected `new_keys` *before* trimming to `max_active` — the key was new, trimmed, and new again forever (H22). Two rules fall out: **compute "what changed" from what survived, not from what was proposed**, and when a cap treats some rows as permanent, give the permanent set its own budget — `keep_pending = max(0, max_active - len(sticky))` reaches zero and terminates the feature the moment the sticky set fills the cap. |
| **A cosine / confidence / similarity threshold that never admits anything** | Plot the distribution before touching the constant; the bar is often outside the range the model can produce. `associative_wander` reported `no_pair` on 107 of 107 runs against a `max_pair_cosine` of 0.25, and the **minimum cosine over all 561 eligible pairs in the live graph was 0.2648** — it missed the corpus floor by 0.015 (H23). Sentence encoders put genuinely unrelated text at 0.3-0.5, not near zero, so a threshold like this encodes an intuition about cosine space that no real encoder satisfies, and it silently breaks again on any model swap. **Prefer a quantile of the observed pairs to a fixed constant** (keep the constant as a sanity ceiling), because a rank cannot be placed out of reach. Same root shape as H21: an absolute threshold is a claim about a distribution nobody measured. |
| **The app reopens the wrong conversation on launch** | The restore pointer is `session.last_active_id` in `config/user.json`, and `_resolve_initial_session_id` honours it **over** the database. Compare it against ground truth: `SELECT session_id, COUNT(*), MAX(created_at) FROM messages GROUP BY session_id ORDER BY 3 DESC LIMIT 5`. If the pointer names something older than the top row, it went stale — it is written on an explicit `switch_session` (intent) *and*, since K91, on the first user turn in a session (activity), so a disagreement now means the write is failing: `persist_user_overrides` swallows errors at debug level, so raise `app.session` to DEBUG and look for `failed to persist last_active_id`. Note the empty-session case is deliberate: "New session" → close → reopen keeps you on the fresh empty one, so a pointer with no messages behind it is not evidence of a bug. |
| **The PWA opens on an empty chat that isn't empty** | History hydration is `useSessionHistory`, called from `App` so it runs on every layout. It used to live in `SessionSidebar`, which the desktop tree always mounts but the phone tree only mounts inside `MobileNavDrawer` — and that returns `null` while closed, so on a phone the socket connected, `hello` set a perfectly good `sessionKey`, and the transcript was simply never fetched. Tell the two apart from the browser console: if `sessionKey` is set and `GET /api/sessions/{key}/messages` never fires, it is the hydration path, not the session. Anything that renders the transcript belongs above the layout branch in `App.tsx`, never inside a conditionally-mounted panel. |
| **She greets you like a stranger at the start of a new conversation** | Expected before K91, and the reason it exists: a new `session_id` empties the transcript, blanks the (session-keyed) rolling summary and K21 thread note, and silences *every* gap cue at once — J5, K14, K28, H21, K36, K34 all measure from the previous assistant message **in the same session**, and a fresh session has none. Check the bridge is rendering: `SELECT chars FROM turn_prompt_blocks WHERE block='continuity_block' ORDER BY created_at DESC LIMIT 5`. Zero rows on the opening turn of a conversation means the gate closed — either `agent.continuity_max_messages` is `0`, this is the first conversation on record (nothing to bridge from), or the previous session's last `created_at` would not parse. A row with no "Where that thread stood" line just means that session never earned a K21 note, which is normal for short threads; the elapsed time is still carried. |
| **A filter rejects 100% of something — before you fix it** | Look at what it was rejecting. A broken gate is sometimes the only thing containing a broken producer: repairing L30's importance plumbing would have released three hypotheses asserting Aiko has a chassis, cooling fans and processing latency, straight into a lane whose output can graduate into her self-model (H7). `scripts/retire_machine_hypotheses.py` both cleans that up and demonstrates the pattern — reuse the *same predicate* for the cleanup and the new gate so they can never disagree about what counts. |
| **Proactive nudge fires wrong / never** | `tail_logs(module_contains="proactive")`. Check `source=prepared|llm` and the skip reasons (`cooldown`, `chat in progress`, `no history`). |
| **Aiko stopped using tools / never calls a tool she should** | P14 tool-pass gate may be skipping the decision pass. Call MCP `get_tool_gate_state` — a `last_decision.reason == "no_signal"` on a turn that *should* have used a tool means the signal-pattern table in [`app/core/session/tool_pass_gate.py`](../app/core/session/tool_pass_gate.py) is missing that phrasing: extend the matching family's patterns (or add the new tool to `_TOOL_FAMILY` — unmapped tools force always-run, so a missing mapping is never the cause of silence). Per-decision trace: `tail_logs(module_contains="tool_pass_gate")` shows one `tool-gate: run=… reason=… matched=…` line per turn; the `turn done:` line carries `tool_gate=` + `tool_pass_ms=`. One-shot repro: `force_tool_pass()` then `send_message(...)` should land `tool_gate=run:force`. Kill-switch: `agent.tool_pass_gate_enabled=false` restores the old always-run behaviour. Escalation ladder (option D small-model router, option B speculative stream) documented in [shipped.md → P14](../docs/personality-backlog/shipped/perf.md#p14-heuristic-tool-pass-gate--skip-the-forced-decision-pass-on-banter-turns). |
| **Aiko never follows up on her own "I'll look into that" / pretends she did** | K43 promise follow-through failure mode. Walk the gates: 1) Call MCP `get_promise_followthrough_state` — confirm `enabled=true` and look at `status_counts.assistant`. No `open` rows at all means the extractor never caught the phrasing (check the assistant patterns in [`app/core/memory/promise_extractor.py`](../app/core/memory/promise_extractor.py) — widen them if Aiko's wording slipped through); rows stuck `open` with an old `last_fired_at` means the idle worker is starved (cross-check `get_idle_workers_status` for the `promise_followthrough` row) or the cooldown/age gates are blocking (`settings` in the same dump). 2) Repro end-to-end: make Aiko say "I'll look into X" → `force_promise_followthrough()` (bypasses age + cooldown) → `send_message(skip_tts=true)` → `tail_logs(module_contains="promise")` should show `promise-followthrough armed:` then `promise-followthrough fire:`, and the Heads-up line lands in `get_last_response_detail.system_prompt`. 3) If the cue fires but Aiko *invents* a result instead of owning that she hasn't gotten to it, that's a persona bug — read the "Things you said you'd do" block in [`data/persona/aiko_companion.txt`](../data/persona/aiko_companion.txt). 4) Promises never flip to `fulfilled`: the lexical matcher needs `memory.promise_fulfil_min_overlap` (default 3) shared content words between reply/task-result and the promise body — grep `promise fulfilled:` at INFO; lower the knob if real fulfilments are being missed. Full reference: [K43 in shipped.md](../docs/personality-backlog/shipped/patterns-k31-k60.md#k43-promise-follow-through--close-the-loop-on-ill-look-into-that). |
| **Slow first token** | Grep `first_token_ms=` over recent turns. If elevated, `set_log_level("app.llm.ollama_client", "DEBUG")` and watch `ollama chat_stream done:` for the per-call `elapsed_ms`. |
| **Wrong provider on a worker / chat path** | "Aiko's chat is hitting OpenAI but a worker is also burning my quota", or the opposite "Why is the chat path still talking to Ollama after I switched to OpenAI?". Call MCP `list_llm_providers` for the catalogue + `list_llm_routes` to see exactly which provider id each role resolves to. Mismatch between expected route and actual client: call `get_client_cache_stats` — each entry shows `provider_ids: [...]` (the providers sharing that slot) so you can confirm route N -> provider P -> cached client C. If a route's `provider_id` is right but the live `_chat_client` was built from a different one, the cascade fired pre-mirror: `set_log_level("app.session", "DEBUG")` and watch for `llm: updated route main_chat -> provider=…` on the next reconfigure. End-to-end retarget without UI: `set_llm_route(role="main_chat", provider_id="openai", model="gpt-5-mini", context_window=131072)` then send a message and verify the next `turn done:` INFO line shows the new `model=`. Full reference: [LLM provider catalogue + role mapping in code-conventions.md](code-conventions.md) and [docs/llm-providers.md](../docs/llm-providers.md). |
| **Low cache-hit rate on OpenAI (high per-turn cost)** | "I switched to `gpt-5-mini` but per-turn cost looks like the *uncached* column on the pricing page." First, confirm the symptom: `rg 'turn done:' data/app.log | rg -o 'cached_pct=[0-9.]+\|prompt=[0-9]+' \| tail -20` — healthy OpenAI sessions settle around `cached_pct=80.0` … `95.0` from turn 2 onward. Numbers stuck near `0.0` mean the prefix is being invalidated turn-to-turn. Step 1: confirm the provider actually returns the field — call `get_last_response_detail` after a turn and look at `usage.cached_tokens`; if it's missing entirely (not just zero), the upstream provider doesn't implement OpenAI prompt caching (Gemini / Groq / most OpenRouter routes — that's a "feature" of the provider, not a bug). Step 2: if cache is supported but cold, `set_log_level("app.prompt_assembler", "DEBUG")` and inspect the `prompt built:` line on two consecutive turns — diff the `providers=` count and `slowest_provider=`. The single most common cause is a per-turn block landing above a stable one (e.g. a new T6 detector got appended into the T1 cluster). Step 3: cross-reference the appended block with `_PROMPT_BLOCK_TIERS` in [`app/core/session/prompt_assembler.py`](../app/core/session/prompt_assembler.py) — if the block is in the wrong tier, move its `if block: system_parts.append(block)` line into the correct cluster (T0 → T6 strictly). Step 4: if the prefix looks right but cache is still missing, the cache may simply be cold — TTL is 5–10 min, so any silence longer than that triggers a full-price re-warm. Step 5: stop guessing which block broke it — set `logging.prompt_cache_log_enabled: true`, hold a normal conversation, and run `python scripts/prefix_break_report.py`. That names the earliest diverging block per turn, what it cost, and whether the provider's `cached_tokens` tracks our prediction (if it does not, the misses are the provider's routing or TTL, not our prompt). Step 6: read the report's **ladder discipline** section rather than fixing the earliest break and re-running. `diverged` names one block and hides every tier behind it, so a fix promotes an unknown successor; the ladder section ranks all tiers' change rates at once and flags an inverted pair (`INVERTED T0_stable (66.7%) churns more than T1_semi_stable (21.7%)`) plus the block filed higher than it behaves. An inversion means either the block is in the wrong tier or its text carries a per-turn-varying value — a monotonic counter or an unquantised float — which must never reach a T0–T2 block. Full reference: [`docs/prompt-caching.md`](../docs/prompt-caching.md) (tier ladder + contributor guide + P44 measurement). |

Fixed in two places: `SessionController._stamp_hypothesis_ask` moves the counter on the real ask, and `expire_stale` now exempts *answered* rows rather than asked ones. Next, check throughput: `SELECT state, surfaced_count, COUNT(1) FROM cue_pool WHERE cue_type='concept_hypothesis' GROUP BY 1,2` — many `pending` rows at `surfaced_count=0` just means the producer outruns the 20h `surface_cooldown_hours`, and they will TTL out harmlessly. Design + the measured numbers: [`docs/hypotheses.md`](../docs/hypotheses.md). |
| **Wrong expression / cry-cascade / lip-sync glitch** | Enable **Settings drawer → Chat → Diagnostics → Debug logging**, reproduce, then grep `data/app.log` for `[ui]` lines. The browser pushes WS events + avatar-channel decisions (`channel.expression applyReaction reaction=… expression=…`) into the same file as the backend timestamps so cause + effect sit side-by-side. See [B6 in personality-backlog/shipped.md](../docs/personality-backlog/shipped/avatar.md#b6-ui-debug-logging-bridge). |
| **Touch gesture didn't fire / persona banner didn't appear / reaction didn't bump axes** | K31 + K32 failure mode — three independent half-paths to walk. **K31 dispatch path**: 1) Call MCP `get_touch_state()` — confirm `enabled=true` and read the per-kind `last_dispatched_monotonic` + `daily_counts` + `daily_date`. If `daily_counts[<kind>] >= cap` for the kind Aiko was trying to use, the dispatch was correctly gated. 2) Force the path bypassing every gate: `send_touch(kind="hug")` returns the dispatched payload — verify the WS `avatar_touch` frame fires (browser devtools → Network → WS → look for `"type":"avatar_touch","kind":"hug"`), the `ReachChannel` lean-in animates in both windows, the chat bubble badge `🫂 Aiko gave you a hug` renders, and the `PersonaActionBanner` appears in the open persona window. If the WS frame lands but no badge / banner — frontend wiring is the suspect; look at `web/src/store.ts` `pushAvatarTouch` + `appendGestureToCurrentTurn` reducers in the React DevTools. 3) Real-gesture trace: `tail_logs(module_contains="touch")` for the per-fire `touch dispatched: kind=hug rejected=false reason=ok` line. If `rejected=true reason=cooldown` / `daily_cap` / `axes_floor` the gate is doing its job — adjust `agent.touch_per_kind_overrides` or wait for axes to climb. **K32 reaction path**: 1) `add_user_reaction(message_id=N, kind="heart")` fakes a click against a real assistant message id (look one up via `get_status` → recent messages). The MCP tool returns the post-apply axes state — if `closeness` moves the apply path works end-to-end. 2) Grep `user_reaction axes:` (INFO level, fires whenever apply moves an axis); if the line shows `applied={...}` but the live axes don't change after a few clicks, the daily cap is exhausted (default `agent.user_reactions_daily_cap_per_axis=0.15`, ~5 hearts per axis per day) — call `add_user_reaction` for `surprise` (signal-only, no axis movement) to verify the inner-life cue still queues. 3) Confirm the multi-window sync: open the chat tab in two browser windows, click 🫂 in one — the other should update within a single WS roundtrip via `message_reaction_updated`. **Persona banner specifically**: gated on `agent.persona_touch_banner_enabled` AND `enabled` prop AND a live `avatarTouchAt` bump AND a backend assistant message id; if everything's set but the banner doesn't show, the source-level test ([`PersonaActionBanner.test.tsx`](../web/src/components/PersonaActionBanner.test.tsx)) documents the exact subscription contract. Full reference + data-flow mermaid: [K31 + K32 in shipped.md](../docs/personality-backlog/shipped/patterns-k31-k60.md#k31--k32-soft-physicality-round-trip--virtual-touch--user-side-reactions). |

### d. Level cheat sheet

The level dial is a contract — every new log call must respect it.

- **ERROR** — only real failures (turn lost, engine crashed, non-2xx). Always shown.
- **WARNING** — degraded paths and retries (model warmup failed, voice switch failed, scheduler job raised but loop continued).
- **INFO** (default) — one structured line per turn (`turn done:`), lifecycle moments (boot, `ollama connected:`, `STT engine ready:`, `TTS engine ready:`, `TTS voice switched:`, `STT capture done:`, scheduler init/shutdown, compaction triggered, proactive spoken).
- **DEBUG** — the tweaking firehose (per-Ollama-call timings, scheduler per-drain summaries, prompt-assembler retrieval breakdown, STT capture lifecycle, TTS enqueue/play, RAG cache hits, full transcript previews).

Three rules about *what* a line says, all of which were learned the
expensive way (H27):

- **A line describing an outbound action is emitted only by the code path
  that performs it.** `privacy scrub REDACT` was logged at INFO by a
  function used both to build search queries *and* as a local yes/no
  detector, so 62 of 284 lines described searches that never happened.
  Detector callers now use `web_safe_probe()`, which is quiet on the happy
  path; `scrub_claim_for_search()` is the one that logs.
- **A line about malformed input carries a bounded preview of the input.**
  `llm-unparseable` without the payload is unactionable, and it hid a
  one-line schema mismatch for two months.
- **Absence needs a cause, not a count.** "found 0 items" and "the model
  returned nothing" must be different lines, or a permanently broken stage
  reads exactly like a quiet evening.

And keep dumps bounded: `dropped=[…]` printed one entry per occurrence, so
scrubbing a transcript produced a 196-element wall of repeated pronouns
that pushed the actual before/after out of view. De-duplicate and count.

Practical presets:

| Goal | How |
|---|---|
| Default | `level=INFO` in config. Turn-by-turn trace + lifecycle. |
| Investigate one module | Keep global `level=INFO`; bump just the relevant module via `set_log_level("app.core.session.prompt_assembler", "DEBUG")` (runtime) or `logging.module_levels` in `config/user.json` (persistent). |
| Production / quiet | `level=WARNING` or `level=ERROR` — a healthy session emits zero log lines. |
| Full firehose | `level=DEBUG` — only when actively tweaking; expect ~hundreds of lines per turn. |

### e. Practical workflow

1. **Before reproducing**: `set_log_level("app.core.<suspect>", "DEBUG")` on the module you suspect.
2. **Trigger the issue**: `send_message(skip_tts=true)` (or use the UI / voice).
3. **Read back**: `tail_logs(module_contains="<suspect>")` for the most recent ring entries, then `read_log_file(grep="turn=<id>")` to widen the lens to the whole turn.
4. **If you need a new field**: open the relevant module, add a structured log line at the right level (use `key=value` so a future grep stays cheap), document the new field in §b above, and restart the app.

### f. Time-travel (DT1 virtual clock)

Much of Aiko's behaviour is time-gated — memory decay and tier promotion, concept confidence decay, anniversaries, gap-return, and the cooldown on nearly every inner-life cue. Logs can only tell you a gate *didn't* open; to see what happens when it does, you used to have to wait. DT1 removes the waiting.

**Arming it.** Start the process with `AIKO_DEBUG_CLOCK=1`:

```bash
AIKO_DEBUG_CLOCK=1 python -m app.web          # bash
$env:AIKO_DEBUG_CLOCK=1; python -m app.web    # PowerShell
```

The gate is an environment variable rather than a setting so it costs a deliberate restart and can never persist itself into `config/user.json` in the on state. Without it the MCP tools are inert and say so.

**Point it at a copy of the database.** Rows written while the clock is shifted keep their virtual timestamps forever — a reset cannot rewrite them.

**Pick the right clock.** This is where people lose time:

| You want to test | Use | Why |
|---|---|---|
| Anniversaries, milestones, cue cooldowns, candidate TTL, promotion age, gap-return | `advance_clock(days=…)` | These read wall-clock `now`. |
| Concept (L3) confidence decay, memory decay, dormancy | `advance_engagement(days=…)` | These read *engaged* time — accumulated active conversation, ~1h per "day". A wall-clock advance does nothing to them. |

Decay is also catch-up-clamped per sweep (`concept_decay_max_catchup_days`, default 3), so simulating a long stretch means interleaving `advance_engagement(3)` with `force_concept_lifecycle` rather than one big jump. Sixty engaged days takes about a minute that way.

**Clean up with `reset_clock`.** It returns to real time and restores the engagement total from the undo anchor that `advance_engagement` stashes on first use. The wall-clock offset is in-memory only, so a restart also clears it.

**What does not move.** Everything on `time.monotonic()` / `time.time()`: turn latency, TTS/STT audio timing, the brain loop, HTTP and orchestrator deadlines, the scheduler's tick budget, worker perf metrics. Log and crash timestamps, task stall detection (`app/core/tasks/`), and outbound weather API dates also stay real. The dividing line is "`datetime` narrative time moves, monotonic runtime timing does not" — see [`app/core/infra/debug_clock.py`](../app/core/infra/debug_clock.py).

Tool reference: [`rules/mcp-server.md` → Virtual clock](mcp-server.md#virtual-clock-dt1).

### g. Frontend crashes

The UI reports its own crashes on a path that is **separate from the log
stream above** and, unlike the `[ui]` debug bridge, is not behind a
toggle: a crash you didn't expect is exactly the one nobody had debug
logging on for. The React error boundary plus the global `error` /
`unhandledrejection` listeners POST to `/api/logs/ui-crash`, which logs
one `ERROR [ui] crash` line and appends a structured entry to
`crashlog.txt`. Read them with **`get_ui_crashes()`**.

What each report carries, in the order worth reading it:

| Field | What it answers |
|---|---|
| `breadcrumbs` | *What led to this.* Last ~60 events, oldest first, stamped `+Nms` from page load. Sources: `console` (every `console.error`/`warn`, so React's own diagnostics are in here), `ws`, `api` (any non-2xx or network failure), `resource` (a failed image/script — a missing Live2D texture explains a lot of later "undefined" errors), plus every existing `debugLog` call site. Repeats inside a second collapse to a `count` so a reconnect loop can't flush the trail. |
| `context` | *What state it was in.* `build` id, `viewport`, `dpr`, `shell` (tauri/browser), `heapUsedMb` / `heapPct`, `visibility`, plus `connection`, `voiceMode`, `route`, `turnInProgress`, `sessionKey`. |
| `stack_mapped` | The stack **de-minified** against `web/dist/assets/*.map`. |
| `component_stack` | The React tree, for `source=render`. |

**On the stack.** A production bundle is minified, so the raw `stack` is
useless on its own; `build.sourcemap` in `web/vite.config.ts` exists to
make it recoverable, and [`app/core/infra/sourcemap.py`](../app/core/infra/sourcemap.py)
does the mapping **server-side** — deliberately, because the crashes
worth catching happen on a phone with no DevTools to attach. Correctness
comes free from Vite's content hashing: `index-D4x9k2.js` only ever
matches `index-D4x9k2.js.map`, so a stale `dist/` produces *no* mapping
rather than a wrong one. That is why both `stack` and `stack_mapped` are
recorded, and why a missing `stack_mapped` means "rebuild happened", not
"symbolication is broken".

**When adding anything that runs in the browser**, prefer
`addBreadcrumb(cat, msg, detail)` from
[`web/src/crashBreadcrumbs.ts`](../web/src/crashBreadcrumbs.ts) over a
bare `console.log` for anything you'd want to see in a post-mortem. It
is in-memory only and costs nothing until a crash reads it.

### h. Native crashes (the process just vanished)

`Windows fatal exception: access violation` in `crashlog.txt` is a
different animal from everything above: a memory fault inside a
C/C++/Rust extension, which kills the process outright. Read these with
**`get_native_crashes()`**.

**Do not debug the Python frame at the top of the `faulthandler` dump.**
A pure-Python statement cannot dereference a bad pointer, so that frame
is not the cause — it is wherever the already-corrupted heap happened to
be touched next, which in practice means the busiest allocation site in
the process. The first such crash we investigated pointed at
`topic_graph._live_to_topic_clusters_locked`, a function that had run
cleanly a hundred times that same hour and turned out to be entirely
innocent; the tell was that the "suspect" code path had succeeded twice
in the three minutes before the fault.

What to read instead, in order:

| Field | What it answers |
|---|---|
| `module` | *Which DLL held the bad pointer.* Resolved from the faulting address via `GetModuleHandleEx`. Usually the whole answer. |
| `exception` / `address` | The Windows exception code and faulting pointer. An address like `0x0000000000000010` means a null-ish struct deref; a wild address means corruption. |
| `duplicate_openmp` / `openmp_runtimes` | Whether the process was in a **supported configuration at all** — see below. Check this before believing any other theory. |
| `minidump` | A `.dmp` under `data/` for native stack walking in WinDbg / Visual Studio. Written without the exception record (dbghelp refuses it from inside a filter with `ERROR_NOACCESS`), so every thread's native stack is there but the debugger won't jump to the fault automatically — the `address` field above is your anchor. |

**Multiple OpenMP runtimes is the first thing to rule out.** Two copies
of one runtime, or two different ones, in a single process is documented
undefined behaviour: each keeps its own global state and thread pool. The
result is a random native fault after hours of uptime — which looks
exactly like failing hardware, and which CPU/RAM stress tests will never
reproduce, so it survives a clean bill of health from memtest or OCCT.
`log_native_runtime_inventory()` logs the tally once at boot through the
`app.native_runtimes` logger, at WARNING when the combination is
unsupported, so grep `native runtimes:` to see what a given run was
carrying.

**Know the expected baseline, or the field is unreadable.** The main
process should map exactly one OpenMP runtime,
`torch\lib\libiomp5md.dll`, and the venv should contain no `vcomp140.dll`
at all. A duplicate in the main process therefore means something
regressed, and the two candidates are worth knowing because both have
happened: **an environment behind `requirements.lock`** (`realtimestt`
0.3.x imports `openwakeword` and `faster_whisper` eagerly, which adds
CTranslate2's copy of `libiomp5md.dll` plus sklearn's `vcomp140.dll` — the
1.x line loads both lazily instead), or **an eager import of the STT
service's dependencies** defeating the `_recorder_class()` deferral. Start
with `pip check` and a diff against the lock; that is seconds of work and
it was the actual answer last time. Note that the *transcription child*
legitimately holds both copies (`faster_whisper` pulls torch via
`transformers`) — on Windows that is a separate `mp.Process`, but
`start_recorder_worker` uses a thread on Linux, so the Docker image puts
that duplicate in the main process. The classification lives in
[`app/core/infra/native_runtimes.py`](../app/core/infra/native_runtimes.py)
— note that it matches curated DLL names rather than substrings, because
`_decomp_lu_cython.pyd` and `_compute.pyd` contain "omp" and make a naive
scan report a pile of runtimes that don't exist.

Those DLLs load on the first *real* STT use, not at import: the
`RealtimeSTT` import in
[`app/stt/realtime_stt_service.py`](../app/stt/realtime_stt_service.py)
is deferred behind `_recorder_class()`, and availability is answered with
`find_spec` so the voice gates don't trigger it. A text-only session
therefore loads no OpenMP at all — which also means the inventory line
differs between a voice run and a text run, and that is expected.

Two caveats when reading the file itself. It is **append-mode**, so dumps
accumulate across runs and the newest is at the bottom; a single header
means a single native crash, no matter how many times the app has died.
And a fatal dump with no matching `native_crash` record predates this
handler — restart to arm it.

## Code Conventions

- Python 3.11+, dataclasses + slots for settings, FastAPI for the HTTP/WebSocket layer.
- LLM calls go through `app/llm/ollama_client.py` (`chat`, `chat_stream`, `chat_with_tools`). Tool dispatch happens in `app/core/session/turn_runner.py` via a pre-stream `chat_with_tools` pass; the streaming reply runs immediately after.
- The agent's available tools are built once per turn from `config.tools` by `SessionController.rebuild_tool_registry()` — see `app/llm/tools/builtins.py` for the live set (`get_time`, `recall`, `web_search`). Other gated tool families: world tools (`tools.world`), and the H11 weather tools `get_weather` / `get_forecast` (`tools.weather`, see [`app/llm/tools/weather.py`](../app/llm/tools/weather.py) and [`docs/weather-sync.md`](../docs/weather-sync.md)).
- TTS text processing (`prepare_tts_text` in `app/core/session/session_text_utils.py`) applies only to the spoken stream, not the chat transcript.
- SQLite (`data/chat_sessions.db`) is the source of truth; LanceDB (`data/lancedb/`) mirrors `memories`, asynchronously indexes `messages`, and holds chunked uploaded `documents`.
- Inline tags Aiko emits: `[[reaction:...]]` (mood label, drives Live2D expression and TTS reaction-to-speed); `[[remember:...]]` / `[[remember:self:...]]` (writes a long-term memory); `[[arc:...]]` (H1 conversation-arc self-tag — one of `casual_check_in / support / planning / reflection / playful / silly`, lands at confidence `0.85` on the regex 0.5 < self-tag 0.85 < smoother 0.95 ladder, see [`app/core/conversation/conversation_arc.py`](../app/core/conversation/conversation_arc.py)); and `[[prosody:...]]` (per-sentence vocal delivery — one of `whisper / soft / slow / fast / firm`, orthogonal to the reaction mood label, applies to the single sentence that opens with the tag, see [`app/core/voice/cadence.py`](../app/core/voice/cadence.py)). All four are stripped from the spoken/chat output before TTS / transcript persistence. Stage-direction earcons (`[[laugh]] [[sigh]] [[gasp]] [[hum]] [[tsk]] [[chuckle]] [[soft_sigh]] [[sharp_gasp]] [[breath]] [[mm]]`) are also inline tags but route through a side-channel earcon player rather than TTS.
- Persona file at [`data/persona/aiko_companion.txt`](../data/persona/aiko_companion.txt) is user-editable, and everything in it is always-on prompt text — the one category that is *not* (conditional handling notes, keyed to the prompt block that triggers them) was moved out to [`conditional_handling.txt`](../data/persona/conditional_handling.txt) beside it precisely so the persona file reads as what it is. See [`docs/cue-pool.md`](../docs/cue-pool.md#the-persona-hoist) before adding a "when your context says X…" section to either. The "Reading {user_name}" section instructs Aiko to mirror the user's register from the live `vocal_tone` and `user_state` prompt cues. The same nudge is mirrored in `_SPEECH_GRAMMAR_ADDENDUM` ([`app/core/session/prompt_assembler.py`](../app/core/session/prompt_assembler.py)) so a deleted/rewritten persona file doesn't lose the behaviour. **Every "Jacob" in the persona has been templated** as the literal placeholder `{user_name}` (Phase 4d). `PromptAssembler._load_persona()` calls `.format(user_name=resolve_user_display_name(...))` once per load; new persona text must keep all braces as `{user_name}` (any other `{...}` token crashes `.format()` and falls back to the raw text via the try/except guard). The legacy backup file `aiko_companion_backup.txt` was deleted — never restore it. **Tool source-of-truth split**: the persona does NOT carry a per-tool catalogue. Every agent tool is already passed to the model natively via the `tools=` parameter (`TurnRunner` -> `chat_with_tools`), and each tool's `schema()` description ([`app/llm/tools/*.py`](../app/llm/tools/) — `builtins`, `world`, `goals`, `file_tasks`) is the imperative, self-contained "what this tool does / when to call it / sync vs async" reference. The persona's "How tools work" block only describes cross-cutting *handling* rules (sync returns inline, async returns a task id whose result lands a later turn, the anti-deferral rule, ask-back-on-disambiguation, never paste raw output). **When adding a tool, put the description in its `schema()` — do NOT re-document it in the persona.** The persona was trimmed ~47% (Phase: persona-trim-tool-budget) by removing this duplication and compressing each K-feature cue section to its essential anti-pattern; the literal `[[...]]` tag vocabulary Aiko must emit (reaction taxonomy, prosody values, `[[remember:...]]` / `[[gap:...]]` / `[[predict:...]]` / `[[arc:...]]` / `[[goal:...]]` / `[[touch:...]]` / `[[conflict:...]]`) was preserved verbatim.
- **Tool under-calling fix — forced choice + escape tool** (NOT reasoning effort). Chatty models (gpt-5-mini especially) lose the implicit "text vs tool" decision on `tool_choice="auto"`: they narrate intent ("I'll list the folders") instead of emitting the call. **`reasoning_effort` is NOT the lever** — minimal / low / medium all defer identically; medium just adds ~8s of latency, so the OpenAI-compat client pins the effort to the cheapest value each family accepts on *every* surface — `minimal` for OpenAI's reasoning models, the per-generation floor for Gemini (`none` on 2.5, `low` on 3.x) ([`app/llm/openai_compatible_client.py`](../app/llm/openai_compatible_client.py)). The actual fix lives in `TurnRunner._maybe_run_tool_pass` ([`app/core/session/turn_runner.py`](../app/core/session/turn_runner.py)): it forces `tool_choice="required"` and appends a synthetic `respond_directly` escape tool (`_RESPOND_DIRECTLY_SCHEMA`, never registered in the `ToolRegistry`). This reframes the choice from "text vs tool" (which the conversational prior always wins) to "which tool" (where `list_file_roots` clearly wins for "what files can you see?"). The pass filters the escape tool out of `response.tool_calls`: if it's the only pick the model is signalling "just answer" and the pass returns WITHOUT appending the tool-calls message (a dangling tool_call with no result would 400 the streaming pass); if a real tool is also picked, only the real one is dispatched. `tool_choice` is a new keyword-only param on `chat_with_tools` across the `ChatClient` protocol + both clients — forwarded to OpenAI-compatible providers, ignored (harmless) by Ollama's Go server. The tool pass caps `num_predict = min(max_tokens, 512)`. Tests: `tests/test_turn_runner_tool_pass.py` (`ForcedChoiceEscapeToolTests` + budget). **If the model still won't call a real tool, the next lever is a focused tool-router system prompt on the decision pass (option B) — NOT raising reasoning effort.** **P14 gate**: the pass no longer runs on *every* turn — a pure heuristic gate ([`app/core/session/tool_pass_gate.py`](../app/core/session/tool_pass_gate.py)) skips it on turns with no tool-shaped signal and no continuity signal (finished-task block / active task / previous turn dispatched a tool / MCP force flag). When the pass does run, the forced-choice + escape-tool semantics above are untouched. **When adding a new tool, add its name to `_TOOL_FAMILY` (and patterns if it's a new family) in `tool_pass_gate.py`** — unmapped tools force the gate into always-run (safe but pays the full TTFT tax again). Kill-switch: `agent.tool_pass_gate_enabled=false`. Debug: MCP `get_tool_gate_state` / `force_tool_pass`, `tail_logs(module_contains="tool_pass_gate")`.

- **File size guidance** — Cursor's indexer slows down on very large source files (we hit it at ~5k lines on `SettingsDrawer.tsx` and `session_controller.py`). Keep Python files below ~1,500 lines and React/TS components below ~1,000 where you can; if a file exceeds ~2,500 lines, schedule a split before adding more. Established split patterns:
    - **Python**: feature mixins under `app/core/<area>/*_mixin.py`. State ownership stays on the host class (`SessionController.__init__` keeps every `self.*` assignment); mixins only group methods. Reference: [`app/core/session/avatar_mixin.py`](../app/core/session/avatar_mixin.py), [`app/core/session/inner_life_providers_mixin.py`](../app/core/session/inner_life_providers_mixin.py), [`app/core/session/speaking_window_jobs_mixin.py`](../app/core/session/speaking_window_jobs_mixin.py), [`app/core/session/post_turn_mixin.py`](../app/core/session/post_turn_mixin.py). Tests that patch `app.core.session.session_controller.<symbol>` for a method that has since moved must patch the **mixin module** instead — the patch must target the module where the symbol is *looked up*.
    - **React/TS**: extract panels and tabs into a feature folder under `web/src/components/<feature>/*.tsx`. Use explicit `Props` interfaces, not parent closures, so the new file is self-contained and source-testable. Reference: [`web/src/components/settings/`](../web/src/components/settings/) (Voice, Avatar, Memory + 5 sub-panels, World, Together, Diagnostics, Identity each in their own file).
    - **Where to put new code** — when extending an inner-life prompt provider, post-turn hook, or speaking-window job, place the new method on the relevant mixin (not on `session_controller.py` directly). When adding a new Settings drawer surface, create a new file under `web/src/components/settings/` with its own `Props` rather than another inline tab block.
- The Settings drawer has a dedicated **Memory** tab ([`web/src/components/SettingsDrawer.tsx`](../web/src/components/SettingsDrawer.tsx)) for inspecting + editing long-term memories. It paginates server-side via `GET /api/memories?limit=&offset=&kind=` (page size 50, response includes `total` + `cap`), with edit-in-place, manual create (`POST /api/memories`, dedupes via the existing cosine-collapse path and toasts "merged into memory #N"), salience editing, kind filter / sort selectors, and a **pin** toggle (`POST /api/memories/{id}/pin`). Pinned rows are **immune to `MemoryStore.decay()` and never selected as `prune()` victims**, and `RagRetriever` adds a `+0.05` score bonus for pinned hits. Pinning lives in SQLite (`memories.pinned`, schema v5) only — the LanceDB mirror is intentionally not aware of it, to avoid a destructive vector-store rebuild on existing user databases. Frontend Zustand state is `memoryView: { items, total, cap, page, pageSize, kindFilter, order }` plus `applyMemoryAdded` / `applyMemoryUpdated` / `applyMemoryDeleted` reducers; `memory_added` only prepends to the visible page when on page 0 with `order=recent` and a matching kind filter (otherwise just bumps `total`). New WS event: `memory_updated`. The default `memory.max_memories` cap was bumped from 500 to 5000 — search remains a sub-millisecond NumPy pass at that size and the LanceDB-backed retrieval is sub-linear, so the headroom is essentially free.
- **Aiko's room** — the [`WorldStore`](../app/core/world/world_store.py) is a small persistent virtual space owned by `SessionController` (one row per location / item, plus a singleton `world_state` row holding posture / activity / current location). Schema v6 (`chat_database.py`) adds the three `world_*` tables; on first boot a "rich default" room is seeded (desk, bed, bookshelf, kitchenette, window seat, beanbag, mirror corner) with matching items (cookies, tea pot, plush blanket, photo of Jacob, monitors, retro keyboard, …). The room reaches the LLM via three seams: (1) the `world` inner-life prompt provider in `prompt_assembler.py` renders a 3-5 line ambient block ending in an explicit "acknowledge your surroundings only when it feels natural — never force a room mention" tonal nudge; (2) five new agent tools (`look_around` / `move_to` / `change_posture` / `inspect_item` / `consume_item` in [`app/llm/tools/world.py`](../app/llm/tools/world.py)) gated by `tools.world` in config; (3) REST under `/api/world` (`GET`, `PATCH /state`, location + item CRUD, `POST /items/{id}/consume`, `POST /seed?force=true`) plus a single `world_updated` WS event carrying typed surgical patches (`{state}` | `{location}` | `{item}` | `{deleted_*_id}` | `{snapshot}`). The Zustand reducer `applyWorldPatch` merges them in place so the new **World** tab in `SettingsDrawer.tsx` stays live. **"Give Aiko a cookie" is intentionally silent** — items appear in her room with `given_by="user"` and Aiko notices them on her next turn through the prompt block, no proactive message is fired. Consumable items (food) decrement on `consume_item` and the row is deleted at quantity zero; non-consumables clamp at zero so the lamp stays in the room.
- **LLM provider catalogue + role mapping** — `llm` is the **only** LLM config block; the old `ollama` and `chat_llm` blocks are gone. Schema on [`AppSettings.llm`](../app/core/infra/settings.py): `llm.providers[]` (slotted `LlmProvider` rows with id / name / kind / base_url / api_key / api_key_env / extra_headers / timeout / keep_alive / think_num_predict_headroom), `llm.routes{}` (role → `LlmRoute`: `provider_id`, `model`, `context_window`, `max_tokens`, `temperature`, `reasoning_effort`), and `llm.embedding` (`LlmEmbedding`: `provider_id`, `model`, `num_ctx`, `num_gpu`). Canonical roles are `LLM_ROLE_MAIN_CHAT = "main_chat"`, `LLM_ROLE_WORKER_DEFAULT = "worker_default"` and `LLM_ROLE_WORKFLOW = "workflow"`; adding e.g. `heavy_workers` needs only a new row in `routes`. **Two routes pointing at the same provider share one underlying `ChatClient`** via [`ClientCache`](../app/llm/factory.py) keyed by `(kind, base_url, resolved_api_key)`; the cache derives a per-provider `OllamaSettings` transport template so each route's `context_window` actually reaches the wire; credential edits invalidate the slot; app shutdown drains the cache. `AppSettings.ollama` still exists as a **derived read-only view** of `routes.worker_default` + `llm.embedding` for the ~40 legacy read sites — never write to it. **Migration is one-shot and persisted**: `_migrate_legacy_llm` synthesises the catalogue from any legacy `chat_llm` / `ollama` blocks found in `user.json`, writes the resulting `llm` block back, and prunes the retired keys via `prune_user_override_keys` (second boot reads the new block directly); the legacy keychain entry is adopted onto the `main_chat` provider's account during secrets hydration. **`update_route` is the single mutation path** — it persists, rebuilds the affected clients, and cascades to the TurnRunner, the proactive director and every worker. REST: `/api/llm/providers` (CRUD + `/{id}/credentials` + `/{id}/test`), `/api/llm/routes` (GET + PATCH), `/api/models/required` (what the routes need vs. what Ollama actually has) and `POST /api/models/pull` (202 + streaming `model_pull_progress` WS events). WS `llm_settings_changed` carries `providers` + `routes`. Frontend: [`LlmProvidersListSection`](../web/src/features/settings/LlmProvidersListSection.tsx) (catalogue list with add-from-preset / edit / test / delete) and [`LlmRoutesSection`](../web/src/features/settings/LlmRoutesSection.tsx) (Role → Provider / Model / Context / Max-tokens table with a free-text model combobox seeded from preset `recommended_models` + the live model list); the old `ChatProviderSection` is deleted. **Code that needs an LLM client should target a role**: read `routes.main_chat` / `routes.worker_default` and pull the provider through `_find_llm_provider(route.provider_id)` + `ClientCache.get(provider)`. **Per-provider wire quirks live in the client, keyed off the model id**, not in the route: Gemini collapses `system` into the first `user` message, pins `api_style="chat_completions"` (it has no `/v1/responses`), and receives an explicit `reasoning_effort` — every Gemini from 2.5 on reasons by default and bills thinking at the output rate, so the preset defaults to `low`, the tool pass drops to the generation's floor, and `none` is clamped to `low` on the tags that can't stop thinking (all of Gemini 3, plus 2.5 Pro). Set a route's effort to `omit` to send nothing and take the provider's own default. MCP debug surface: `list_llm_providers`, `list_llm_routes`, `set_llm_route`, `get_client_cache_stats` — first stop when "which provider is this worker actually hitting?" comes up. See [`docs/llm-providers.md`](../docs/llm-providers.md) for the full design.
- **Prompt-cache prefix-stability ladder** — `PromptAssembler.assemble_with_budget` lays `system_parts` out from most-stable (T0) to most-volatile (T6) so OpenAI's prompt cache hits the longest possible prefix on every turn. The contract is encoded twice — once as the audit constant [`_PROMPT_BLOCK_TIERS`](../app/core/session/prompt_assembler.py) near the top of the file, and once as the literal `if block: system_parts.append(block)` cascade further down. The tiers, with one-line examples: **T0 stable** (persona, grammar addenda, profile, petname, catchphrase, voice_adoption) → **T1 semi-stable** (relationship, anniversary, milestone, axes, arc, agenda, goals, coactivation, day_color) → **T2 summary** (compaction-only) → **T3 `relevant_context`** (the unified context budget: memories + topic clusters + concepts, all turn-relevance-scored against one shared per-turn embed and selected to fill a shared, context-window-relative token budget — this **reserved-before-history** region subsumes the retired standalone `memory_block` / `interest_map_block` / `concept_block`; on overflow history is squished first and the region degrades last; see [`docs/context-budget.md`](../docs/context-budget.md)) → **T4 ambient** (grounding line, world, activity, circadian, pajama, ambient noise, sensory anchor) → **T5 affect / style** (affect, mood hint, mood shell, style signal, user state, vocal tone) → **T6 detectors** (everything that takes `user_text` as input: novelty, stagnation, clarification, belief gaps, knowledge gaps, opinion injection, …). **When adding a new prompt block, pick the tier that matches the block's lifetime, append it inside that tier's `if` cluster, and add its name to `_PROMPT_BLOCK_TIERS`.** Cross-tier inversions are caught by `tests/test_prompt_assembler.py::PromptCachePrefixOrderingTests` (persona < affect, profile < memory, summary < memory, memory < detectors, …), and `PromptLadderOrderTests` parses the cascade out of the source to assert the constant lists blocks in the order they are actually appended — that ordering is load-bearing for P44's `lost_chars`, not just documentation. Observability: `ChatUsage.cached_tokens` is lifted from `prompt_tokens_details.cached_tokens` on every OpenAI response, surfaces on the `turn done:` INFO line as `cached=N cached_pct=%.1f`, rides the per-turn WS metrics as `cached_tokens` / `cached_pct`, and is mirrored on MCP `get_last_response_detail`. **P44 divergence telemetry** answers the next question — *which* block ended the cacheable prefix. [`prompt_prefix_telemetry.py`](../app/core/session/prompt_prefix_telemetry.py) hashes every registered block per turn (`block_hash_table`, the sibling of `block_char_table`), and the pure `diagnose_divergence` reports the earliest change in ladder order, the chars lost at and after it, and whether history diverged by a window *slide* (expected) or by messages being *rewritten in place* (`history_slid == -1`, the fingerprint of the K-time1 age prefixes). Records go to `data/prompt-cache.jsonl` via the `app.promptcache` logger — `propagate = False` so they never reach `app.log` — gated behind `logging.prompt_cache_log_enabled`, **off by default**; read back with `scripts/prefix_break_report.py`. Note the UI's per-block breakdown rows are *rescaled* onto the provider's real prompt-token count (`_estimate_scale`), because the char heuristic and a real tokenizer cannot agree; the JSONL deliberately records the **raw** estimate so `est_error_pct` stays meaningful. Ollama and most non-OpenAI providers leave the field at `0`, which is the correct null answer. Workers share the same `ChatClient` but write to a *different* cache slot (their `messages[0]` is not Aiko's chat system prompt), so worker calls do not invalidate the chat cache nor share its discount. Full design + worked pricing example: [`docs/prompt-caching.md`](../docs/prompt-caching.md).

- **Memory tiers + revival drift + IdleWorker framework (schema v8)** — Long-term memory is no longer a flat pool. Every row in [`memories`](../app/core/memory/memory_store.py) now carries a `tier` (`scratchpad` / `long_term` / `archive`) and a `revival_score` in `[0, 1]`. Auto-extracted observations (`MemoryExtractor`, `ReflectionWorker`, `DreamWorker`) land in `scratchpad`; verified anchors (`PromiseExtractor`, `CatchphraseMiner`, `SharedMoments`, `RelationshipPulse`, `[[remember:...]]` tags via `TurnRunner`, manual REST/UI adds, milestone memories) write directly to `long_term`; pinned rows are always coerced to `long_term`. `MemoryStore.decay` is now **wall-clock-driven** (proportional to elapsed time since `memory.last_decay_run_at` in the new `kv_meta` key-value table, clamped by `decay_max_catchup_days`) with per-tier rates and a revival rebate (`salience += revival_coefficient * elapsed * revival_score`). `prune()` enforces per-tier caps independently. **Revival detection** (`SessionController._mark_revived_memories`) runs post-turn: it reads the surfaced-IDs snapshot off `RagRetriever.last_surfaced_memory_ids` and bumps `revival_score` on memories whose content shares ≥ `revival_min_word_overlap` (default 3) content words with Aiko's reply. A new **`IdleWorkerScheduler`** (`app/core/proactive/idle_worker_scheduler.py`) runs background workers during quiet windows (gated by `SessionController._is_user_idle`: no Live mode, no turn in flight, no recent user activity); it caps one worker per tick to avoid stacking and persists `last_run_at` per worker to `kv_meta`. First two workers: [`MemoryPromotionWorker`](../app/core/memory/memory_promotion_worker.py) (promotes scratchpad rows on age + use_count OR revival ≥ threshold, demotes idle long_term rows after 180 days, deletes dead scratchpad, coerces pinned, then re-runs prune) and [`MemoryDecayWorker`](../app/core/memory/memory_decay_worker.py) (thin wrapper around `MemoryStore.decay`). Both default to hourly cadence (configurable down to seconds for testing). **New REST endpoints**: `GET /api/memories/counts`, `tier=` query param on `GET /api/memories`, `tier` on PATCH/POST. **Frontend**: Memory tab grew a tier pill, tier filter, per-tier counts header, and a revival % readout when `revival_score > 0.05`. **All new background jobs should register with the `IdleWorkerScheduler` rather than spinning up their own threads** — F1 (fact-checker), G2 (schedule learner), G3 (curiosity worker), and any other "run me when nobody's talking" task fits the same protocol. See [`docs/memory-tiers.md`](../docs/memory-tiers.md) for the full design + producer rules.

- **Demand-driven idle scheduling (P36)** — full reference in [`docs/idle-workers.md`](../docs/idle-workers.md). A worker's `interval_seconds` is a **heartbeat** (liveness backstop), not a cadence. What decides whether it runs is an optional `demand()` probe returning a [`WorkSignal`](../app/core/proactive/idle_worker.py) — `pressure` in `[0, 1]` for how much work is pending, plus `needs_llm` for whether *this* run will call a model. [`IdleWorkerScheduler`](../app/core/proactive/idle_worker_scheduler.py) ranks by urgency (`0.7 * pressure + 0.3 * staleness`) instead of by age, and splits its budget into a **compute lane** (`idle_worker_compute_budget_ms`) and an **LLM lane** (`idle_worker_tick_budget_ms`, which was always really a GPU-contention limit). Compute drains first within a tick, so cheap arithmetic never queues behind a generation. The LLM lane is sized by [`classify_contention`](../app/core/proactive/llm_contention.py) comparing the `main_chat` and `worker_default` routes — `none` / `queueing` / `swapping` — and both lanes scale with idle depth (`just_left` 1x → `overnight` 10x, persisted to `kv_meta` so a restart mid-absence does not reset it). **When adding or migrating a worker:** implement `demand()`, and split `is_ready()` in two — hard vetoes (feature flags, cold-start guards, rate limiters) stay, the `default_is_ready(self.interval_seconds, …)` timing check moves into the probe. Leaving the timing check in `is_ready()` vetoes the worker before its pressure is ever read, silently disabling the mechanism for it. The probe must be far cheaper than `run()` (a `COUNT`, a `kv_meta` read, an in-memory mirror scan); one whose EMA passes 50 ms is dropped back to interval scheduling automatically. Set `needs_llm` per *run*, not per worker. Returning `None` means "no opinion, schedule me the old way" — all fifty-five workers report demand today, so that path now only catches a probe that failed. **A probe must not mutate, and must not consume a force flag or a rate token**; where the cheap read does not exist, factor a read-only helper out of `run()` and call it from both sides. Calibrating `pressure` is harder than making it cheap and the suite cannot see a miscalibration, so check a migration against a real log — [five specific ways a probe goes wrong](../docs/idle-workers.md#five-ways-a-probe-goes-wrong). Debug with the `probe_idle_worker_demand` and `force_idle_worker` MCP tools. **Config rule: a deleted config key must be replaced by the worker knowing something, not by a hardcoded constant** — that is the bar for retiring the remaining `*_interval_seconds` and `*_per_hour_cap` keys (P44 / P45).

- **The cue pool (schema v29)** — full reference in [`docs/cue-pool.md`](../docs/cue-pool.md). One `cue_pool` table + [`CueStore`](../app/core/proactive/cue_store.py) replacing the three incompatible bookkeeping shapes the seven subject-naming cue workers used (a `kv_meta` ring plus a `surfaced_keys` set; a ring plus a watermark plus an in-memory slot; rows in `memories`). It exists to answer two questions none of those could. **How much stock do I have** — a worker counts pending rows and reports pressure from the *deficit* against `CuePolicy.inventory_target` (`pressure_from_deficit`, via [`CueProducer`](../app/core/proactive/cue_producer.py)), which is what retired the five hand-picked `*_daily_cap` keys: a full shelf means the scheduler simply does not admit the worker. **Was it used** — a cue moves `pending → surfaced` when it reaches the prompt and only reaches `used` when post-turn matching finds its *subject* (not its sentence) in what was actually said; otherwise it returns to `pending`, bounded by two separate counters (`surfaced_count` = she was shown it and did not raise it; `ask_count` = she raised it and got no answer) that each expire it independently, which is what makes the retry loop safe when the matcher is wrong. Consumption lives in [`CuePoolMixin`](../app/core/session/cue_pool_mixin.py) and is two `echo_detector` calls, never an LLM; `fulfilment=answered` types take a second stage on the *next* turn (`awaiting`), because if she asks about X and the user answers about Y the curiosity is not satisfied. Per-type behaviour is one registry — `CUE_POLICIES` in [`cue_accounting.py`](../app/core/proactive/cue_accounting.py). **The one rule that is easy to get wrong: a cue whose subject is on-topic by construction must stay `match_mode=lexical`** — for `knowledge_gap_notice` ("I keep circling X and never dug in") a high cosine against her reply measures "she stayed on topic", not "she used the cue"; the cosine is still computed and recorded in `used_evidence` so the floors can be set on evidence later. A type that is rare by *nature* rather than by scarcity also sets `surface_cooldown_hours`, which gates how often a **new** cue of that type may be claimed (never a retry — an in-flight cue is unfinished business); it exists because deficit-driven production removed the accident whereby a worker on a ten-day cooldown drafted one cue a fortnight and therefore surfaced one a fortnight. Each policy also names a `handling_section` + `block` — a persona header that `PromptAssembler._persona_split()` hoists out of T0 and `_render_handling_notes(locals())` re-attaches in T6 only when that block actually rendered. **The hoist long outgrew the cue pool**: 51 blocks and ~44 k chars off every turn, against a persona now down to ~35 k, and most of them are not pool cues — a block only has to be *rare* to qualify, so the turn-taking permissions, topic-pitch reads, repair detectors and register nudges register in `HANDLING_SECTIONS` in [`prompt_support.py`](../app/core/session/prompt_support.py) instead. The pairing is many-to-many (one renderer may claim several headers; one passage may cover a family, e.g. the three repair detectors), so `_persona_split` resolves each header once and `_render_handling_notes` dedupes. The resolver reads the assembly frame's locals, so adding one needs no edit at the call site. Two things deliberately did *not* hoist, both recorded in `prompt_support.py` and both guarded by `tests/test_persona_hoist.py`. `_STAYS_IN_T0` holds the blocks that read like cues but render most turns, and **the entry criterion is the provider, not the prose** — `goals_block` says "your context *may* include" and renders whenever one goal is active, which the onboarding seed guarantees from first run; `grounding_block` is the inverse trap, off by default (so a stock install carries a section for a block that never fires) but on essentially every turn once `grounding_line_mode` is enabled, so hoisting optimises the configuration nobody using the feature is in. The second list is the sections interleaving always-on inline-tag grammar with one block's handling: `split_persona_section` moves whole sections, so a wholesale hoist takes `[[remember:]]` or `[[moment:]]` with it and the tag silently stops being taught. Three were split by hand into their own headers (`follow_up`, `anniversary`, `growth_witness`); two more — `arc_block`, `knowledge_gaps_block` — turned out to have no conditional half at all, since both emit *content* rather than handling for content, leaving their persona sections as pure tag grammar. See the hoisting rule in [`docs/prompt-caching.md`](../docs/prompt-caching.md). **Not every pooled cue comes from a worker.** The gap-return trio (`turning_over`, `sleep_return`, `away_activities`) is armed by an event carrying no content and picks what to say when the block renders, so `CuePoolMixin.record_surfaced_cue()` writes the row *at* surface time, already `surfaced`; `long_arc_callback` uses the same ledger for a stronger reason (its candidate *is* a RAG hit against the message being answered) and pairs it with a `relevant` predicate — `long_arc_callback.still_relevant()` — so a released callback only comes back on a turn that is still about it; `self_correction` and `tease_ledger` are queued from the turn path by `CuePoolMixin._queue_pool_cue()`, since a contradiction only exists once Aiko has said the contradicting thing, and a mock-grudge only exists once the user has said the thing being held against them. All six set `inventory_target=0`, which is what tells the scheduler their empty shelf is the resting state and tells `armed_cues()` that a queued or released row is an opportunity on its own. **`tease_ledger` (K59) is the migration to read before doing another one**: it replaced a private `kv_meta` store rather than a schedule, deleting hand-written cap / expiry / offer-stamp / settle / re-offer logic, and it is where the shared defaults turned out to be actively wrong twice. Its cues want to be *stale* (the gap between banking and collecting is the joke), which is what `CuePolicy.pick_order=oldest` and the `hold_hours` seal on `add()` exist for; and its subject has to be the user's quote rather than the cue's own `what`, which is a **constant** on the K29 pushback lane — keyed on that, every new debt would have superseded the last, and matched on that, any reply containing "pushed"/"back"/"hard" would have settled an unrelated one. Three gates stayed outside the policy because no field expresses them: a relationship-axis floor, a cooldown the J11 affection-style bias divides (so `surface_cooldown_hours=0` and the renderer spends it against `last_surfaced_at`), and a near-duplicate check, because the pool supersedes on an *exact* subject and a quote reworded is the same grudge. **A cue can also name a subject and still belong outside the pool**: `promise_followthrough` keeps its state in `memories` (the commitment, its lifecycle, and the post-turn hook that decides whether she made good on it), so pooling it would put two stores in charge of one question — it takes `demand()` from its pending kv slot plus its arm cooldown and nothing else. Surfaces: the Memory tab's Cues panel over `GET /api/cue-pool` + the `cue_pool_updated` WS event, and the `pool` section of the `get_cue_outcomes` MCP tool. Terminal rows are never deleted — "offered four times, never taken" is the satisfaction evidence. **The test for whether a cue belongs in the pool at all: if Aiko acts on it, will her reply contain its subject?** Consumption is a subject match, so a cue that changes *how* she speaks rather than *what* she says (`absence_curiosity`, `mood_inertia`, `mood_drift`) would score every perfect firing as a miss; those stay off the pool and hoist their handling text through `HANDLING_SECTIONS` instead.

- **Higher-order concept layer (L1–L3, schema v21–v23)** — A cross-cluster abstraction tier above topic clusters. Discovery/lifecycle "aha!" events feed the append-only [`ConceptEventStore`](../app/core/concepts/concept_event_store.py) timeline. Decay across L3 + the memory decay worker is driven by the shared [`EngagementClock`](../app/core/infra/engagement_clock.py) (active-conversation time, not wall-clock). **L5 surfacing + recall (user slice):** active user-identity concepts render as hedged, confidence-scaled impressions — now folded (with memories + topic clusters) into the T3 `relevant_context` region built by [`build_relevant_context`](../app/core/session/inner_life_part1.py) under the unified context budget (the standalone T1 `concept_block` / `interest_map_block` were retired; the concept trace now rides back on the returned `RelevantContext` rather than the `_StaticSlices` cache). The `recall_concept` tool ([`RecallConceptTool`](../app/llm/tools/builtins.py) → [`RagRetriever.recall_concept`](../app/core/rag/rag_retriever.py)) returns a one-call bundle (concept + capped evidence memories + cluster labels, `all_evidence` flag for the full set). **L21 cold-start guard:** `TopicGraph.mature()` (+ `MemoryStore.earliest_created_at()`) gate the L2 proposer (`force` bypasses) and drive L3's stricter young-graph promotion bar; every consumer degrades to silent/empty while immature. **L4 cluster co-activation:** [`TopicGraph.cluster_coactivation`](../app/core/conversation/topic_graph.py) detects which clusters "light up together" — one bulk mirror snapshot → per-bucket co-firing rep sets → pairwise Jaccard → connected-component `CoactivationMode`s (coarsely cached, empty in non-persistent mode). The bucket axis is a **strategy registry** (`_BUCKET_STRATEGIES` over an extensible `_CoactMember` snapshot; adding an axis = one pure fn + optional snapshot field, the accumulator is axis-agnostic); only `session` ships (roadmap: `day`/`window`/`circadian`/`weekday`/`gap_session` cheap, `mood`/`arc`/`world_context` join-gated; semantic similarity deliberately excluded). Two consumers: the L2 `identity_user` proposer renders it as a soft "TOPIC MODES" grouping hint (`ConceptSynthesisWorker._coactivation_modes`), and the T1 `coactivation_block` ([`_render_coactivation_block`](../app/core/session/inner_life_part1.py), after the goals block, gated by `agent.coactivation_block_enabled`) renders one hedged "you keep circling X/Y/Z together, meanwhile W went quiet" line. **L26 concept trace + observability:** the L5/L4 renderers stamp a structured trace at selection time on `self._concept_block_trace` / `_coactivation_block_trace` (surfaced concept ids/confidence/plasticity/hedge or a `reason`; co-activation mode + quiet cluster). Because both blocks are slice-cached (`_StaticSlices`), paired `concept_trace` / `coactivation_trace` providers (`set_inner_life_providers`) capture it into `_StaticSlices.concept_trace` / `.coactivation_trace` at build time, and `assemble_with_budget` forwards it to `PromptTelemetry.concepts_surfaced` / `coactivation_surfaced` (tagged `slice_cache_event` + `aggressive`) → `_last_metrics` → `get_last_response_detail`. Three MCP tools in [`proactive_task_tools.py`](../app/mcp/server_tools/proactive_task_tools.py): `get_last_concept_trace` (per-turn), `get_concept_graph` (`concepts_snapshot()`), `get_concept_transitions` (`concept_timeline()` filtered to lifecycle events). **L9 living beliefs (contradiction):** a read-only [`ConceptContradictionDetector`](../app/core/concepts/concept_contradiction.py) reuses the F5 three-tier gate concept-vs-memory (cosine band → `classify_pair` → LLM `YES`/`NO` for borderline, its own `FactCheckRateLimiter` `state_key="concept_contradiction.rate_state"`); on a confirmed hit L3 applies [`apply_contradiction_penalty`](../app/core/concepts/concept_lifecycle.py) (plasticity-damped downward step) and, below `concept_contradicted_confidence_floor`, flips `active → contradicted` (a revivable "actively disproven" status, above the dormant floor; excluded from L5), emitting a `contradicted` event on every confirmed disproof. Detection rides L3's `list_stalest` round-robin — `concept_contradiction_batch_size` active concepts checked/tick — so it never sweeps the whole active set; L3 stays the single writer (the detector only reads). Pinned memories are never touched; bounded per tick by `concept_belief_revision_batch_size` concepts × `_max_evidence` memories. L3 stays the single writer of *concept* state — the reviser writes only *memory* state, like F1 / F5. **L16 plasticity governor:** `plasticity` is the single per-concept learning rate the L3 engine damps *every* confidence move by, symmetric in both directions — decay (`halflife *= 2 - p`), accrual ([`accrual_alpha`](../app/core/concepts/concept_lifecycle.py), step `0.5 + 0.5*p` of the gap to target), L9 disproof, and the L15 revision cut — so a sticky (low-plasticity) core trait resists change and needs more evidence to promote; `p=1` reproduces the pre-L16 full snap. Per-kind default bands live on `ConceptKind.plasticity_default` ([`concept_kinds.py`](../app/core/concepts/concept_kinds.py); identity low via `concept_identity_plasticity`, else `concept_default_plasticity`), stamped on first eval. **The deferred L16 block (all three pieces) is now shipped, general + per-kind:** (1) **relationship modulation** — the L3 worker computes an **effective** plasticity at eval time via the pure [`effective_plasticity`](../app/core/concepts/concept_lifecycle.py)`(base, signal, mod)`, lifting a kind's stored base by the live trust + relationship-duration `RelationshipSignal` (built in [`speaking_workers_init_mixin.py`](../app/core/session/speaking_workers_init_mixin.py) from `relationship_axes` trust + `relationship` duration). "Never silently": each modulation upserts one `signal:relationship_trust --influences--> concept` edge and, on a band cross (vs. the prior edge strength, `concept_plasticity_shift_event_delta`), emits a `plasticity_shift` event. (2) **plasticity-drift** — a settled *active* concept's **stored** plasticity is nudged one-way down toward `concept_plasticity_drift_floor` via [`drift_plasticity`](../app/core/concepts/concept_lifecycle.py), scaled by confidence + engaged age (stickier with time; skipped on first eval). Modulation is read-live + additive-only (loosens, never tightens below base); only drift mutates the stored base — the two stay independent. - **Temporal awareness contract (K-time)** — The other half of the "now" seam above: `now()` answers *when is it*, this answers *how does written text stay true as it ages*. The regression it exists to prevent already happened once — [`format_transcript()`](../app/core/infra/timephrase.py) shipped complete in `dd2ab58` with a docstring naming "promise / belief / moments / summary" as its callers, and **not one of them ever called it**, so 78% of the memory corpus accumulated as untagged `durable` rows and Aiko began speaking about things from May in the present tense. A good toolkit with no stated contract rots. **The toolkit, and which helper is for which job:** `today_anchor()` puts the current date in a worker's *system* prompt; `format_transcript()` renders `[Sat 14:30] Speaker: text`; `format_memory_block()` / `format_memory_line()` render *always*-tagged memory bullets for a worker prompt; `age_prefix()` is the K-time1 history band; `temporal_suffix()` is the v10 tense tag for chat RAG; `has_relative_deictic()` is the write-boundary predicate; `resolve_deictics()` rewrites frozen text against its own write time; and `STORED_TEXT_TIME_RULE` is the one canonical anti-relative sentence — **paste the constant, never retype the wording**. **The chat/worker split is deliberate and must not be collapsed:** chat RAG tags a bullet `(noted 3 days ago)` meaning "when I wrote this down", while `temporal_suffix()` tags `(3 days ago)` meaning "when it happened" — the persona keys off exactly that difference ([`aiko_companion.txt`](../data/persona/aiko_companion.txt)), so conflating them teaches Aiko that every note is an event. Worker rendering has no such distinction and tags everything, because a worker is reasoning about freshness rather than speaking. **Three defensive layers, and which to reach for:** *rendering* ([`rag_retriever.format_block`](../app/core/rag/rag_retriever.py)) fixes presentation for the rows already in the database, which is why no backfill was needed; the *write guard* in [`MemoryStore.add()`](../app/core/memory/memory_store.py) reclassifies a `durable`/`preference` row whose text contains a deictic to `past_event` anchored at write time (it never edits the text — mis-tagging is recoverable, rewriting what was recorded is not) and covers all ~35 producers plus anything added later; the *prompt* is where it should actually be prevented. Reach for the lowest layer that can see the problem. **Cue text has its own failure mode**: it is frozen at draft time and pending rows have surfaced 44 hours later, so `CuePoolMixin.take_pool_cue` appends a "you first noticed this yesterday" note past 6h (on a copy — post-turn accounting must judge the producer's original text), and the render sites that quote raw `mem.content` call `resolve_deictics` against the *source memory's* timestamp, which is a different and usually much older anchor than the draft time. **Deliberately exempt, so nobody "fixes" them:** `memory_conflict_worker` compares two memories for logical contradiction and ages would be noise in that judgement; `idle_curiosity_worker` writes about the world rather than about the user. **Checklist for a new LLM worker:** anchor (`today_anchor()`), tagged input (`format_transcript` / `format_memory_block`), the anti-relative rule (`STORED_TEXT_TIME_RULE`) if its output is stored — and note that `temporal_type` **defaults to `durable`, which renders with no tag at all**, so a worker writing events must pass `past_event` explicitly rather than trusting the backstop. Tests: `tests/test_timephrase.py`, `tests/test_memory_temporal.py`.

- **Conflicting-memory detector (F5, schema v11)** — Hourly background worker [`MemoryConflictWorker`](../app/core/memory/memory_conflict_worker.py) scans the in-memory mirror for pairs of allow-listed memories (`fact` / `preference` / `relationship` / `event`) whose cosine similarity falls in `[0.80, 0.92)` and runs them through a hybrid contradiction gate: a pure-Python heuristic ([`conflict_heuristics.classify_pair`](../app/core/memory/conflict_heuristics.py) — negation flip, antonym table, numerical mismatch) labels each pair `definite` (auto-resolve, no LLM), `borderline` (LLM YES/NO/UNRELATED check via a dedicated [`FactCheckRateLimiter`](../app/core/memory/fact_check_rate_limiter.py) with `state_key="conflict_detector.rate_state"`), or `no` (drop). Confirmed conflicts with `|conf_a - conf_b| >= 0.30` (default) auto-demote the loser to `tier=archive`, `confidence=0.20`, with `metadata.superseded_by` stamped; the rest land in the new schema-v11 [`memory_conflicts`](../app/core/infra/chat_database.py) table with `status='open'` and surface in the new Conflicts sub-tab on the Memory drawer via `GET /api/memory-conflicts` + `POST /api/memory-conflicts/{id}/{resolve,dismiss}` in [`app/web/server.py`](../app/web/server.py). [`MemoryConflictStore`](../app/core/memory/memory_conflict_store.py) registers a delete-listener on `MemoryStore` so removing one half of a pair cascade-cleans the conflict row. Aiko can also self-flag mid-turn with `[[conflict:short reason]]` (parsed in [`response_text_service.py`](../app/core/services/response_text_service.py), stripped from chat/TTS, dispatched in `SessionController._post_turn_inner_life` to `IdleWorkerScheduler.force_run` so the worker runs immediately). Per-tick caps `conflict_detector_max_corpus=1000` and `conflict_detector_max_pairs_per_run=50` bound the O(n²) sweep; per-hour/per-day caps `conflict_detector_per_hour_cap=6` / `_per_day_cap=30` bound the LLM spend. **MCP-debuggable**: like the other idle workers, the scheduler exposes `force_run("memory_conflict_detector")` for hand-inserted contradictions, and the per-turn `Aiko flagged conflict:` INFO log line shows up in `tail_logs` for end-to-end tracing. Tests: `tests/test_conflict_heuristics.py`, `tests/test_memory_conflict_store.py`, `tests/test_memory_conflict_worker.py`, plus extensions to `tests/test_response_text_service.py` and `tests/test_web_server_memories.py`.

- **User-correction detector (F13)** — The contradiction family's fourth corner, beside F5 (two stored memories clash), K29 (Aiko's stance vs. the user's claim) and K38 (Aiko's reply vs. her own fact): F13 catches the **user explicitly correcting a stored fact** and supersedes it. Split hard into a cheap turn-path gate and an expensive off-turn worker so latency is untouched. The pure, embedding-free [`user_correction_detector.detect_user_correction`](../app/core/conversation/user_correction_detector.py) (sibling of `self_correction_detector`) requires an explicit correction marker (`, not my …`, `no, it's …`, `I never said`, `actually it's …`) **and** a content-word overlap with a candidate, only ever over durable-truth kinds (`fact` / `preference` / `relationship` / `event`) — **never a `self` stance row**, which is the correction-of-fact vs disagreement-of-opinion boundary (opinion pushback is K29's lane). `PostTurnHelpersMixin._maybe_capture_user_correction` (in [`post_turn_helpers_mixin.py`](../app/core/session/post_turn_helpers_mixin.py), beside the K17/K38 hooks) runs it against the rows RAG surfaced last turn (`RagRetriever.last_surfaced_memory_ids`, falling back to a kind scan) and stashes a hit on the bounded `_pending_correction_candidates` deque — no LLM, no writes on the turn path. The off-turn [`UserCorrectionWorker`](../app/core/memory/user_correction_worker.py) (registered in `idle_workers_init_mixin.py` next to F5, its own `FactCheckRateLimiter` `state_key="user_correction.rate_state"`) drains the queue, confirms each candidate with a one-line-JSON `YES`/`NO` + corrected-fact LLM call, and on `YES` writes the correction via `MemoryStore.add(confidence=0.9)` **and** demotes the corrected row via `MemoryStore.update(confidence=0.20, tier="archive", metadata.superseded_by=…, superseded_reason="user_correction", metadata_merge=True)` — the exact F5 supersede stamp. Finally it arms a one-shot `user_correction` T6 cue (policy in [`cue_accounting.py`](../app/core/proactive/cue_accounting.py), rendered by `_render_user_correction_block`, block in the "own what you owe" cluster of `_PROMPT_BLOCK_TIERS` after `self_correction_block`; handling text lives under `Owning a correction (the user set me straight):` in [`conditional_handling.txt`](../data/persona/conditional_handling.txt)) so Aiko owns the slip once, naturally — never "I've updated my database". Settings: `agent.user_correction_enabled` + `_per_hour_cap` / `_per_day_cap`; `memory.user_correction_{min_confidence,min_overlap,max_candidates,interval_seconds,max_per_run,concept_penalty,confidence}`. Tests: `tests/test_user_correction.py`.

Stored as a **real column** (schema **v30**, mirroring the `temporal_type` precedent): [`chat_database.py`](../app/core/infra/chat_database.py) bumps `_SCHEMA_VERSION` to 30, adds `provenance TEXT NOT NULL DEFAULT 'inferred'` to the fresh `memories` CREATE, and backfills legacy rows via a guarded v29→v30 `ALTER`. - **Surprise / novelty detector (K6)** — Per-turn signal that lets Aiko react with real surprise when Jacob pivots away from the recent topic baseline. No schema change; the detector is purely in-process. The [`NoveltyDetector`](../app/core/conversation/novelty_detector.py) keeps an in-memory `collections.deque[np.ndarray]` of size `novelty_window=12` on each `SessionController`, lazily warmed once per session from [`RagStore.list_recent_user_vectors`](../app/core/rag/rag_store.py) filtered to `role='user'` rows whose `session_id` starts with the current user prefix (so a topic discussed yesterday won't re-fire "this is new" today). On every turn it embeds `user_text` via the shared `Embedder`, computes `distance = 1 - cosine(vec, centroid)` against the renormalised mean of the ring, classifies into `strong_novelty` (≥ 0.55), `mild_shift` (≥ 0.35), or silent, and appends the new vector to the ring so the baseline keeps moving. A `novelty_cooldown_turns=2` suppression window prevents back-to-back "you keep saying surprising things" beats; cold-start installs stay silent until the ring fills past `novelty_warmup_min=3`. The signal surfaces through a new `novelty` inner-life provider on [`PromptAssembler`](../app/core/session/prompt_assembler.py) (same shape as F2 `knowledge_gaps`: takes the live `user_text`, lands right after `belief_gaps_block`, dropped under `aggressive=True`). Two-band copy lives in the persona block ("Surprise and novelty" in [`aiko_companion.txt`](../data/persona/aiko_companion.txt)). The detector also exposes `last_distance` / `last_band` attributes (additive, no behaviour change for K6 callers) so the K18 sibling can read the per-turn measurement without re-embedding. **MCP-debuggable**: the detector module logs one INFO line per turn — `novelty-detector: distance=%.3f band=%s window=%d user=%s` — plus a one-shot `novelty-detector: warmed ring=N user=X` on first detect; both grep-friendly via `tail_logs(module_contains="novelty")`. To repro a hit end-to-end: send three on-topic messages (e.g. about debugging Python), then one wildly off-topic (e.g. about bee-keeping), and watch the next inner-life block include "Heads-up: Jacob just brought up something well outside the recent baseline." Tests: `tests/test_novelty_detector.py`, plus extensions to `tests/test_prompt_assembler.py` and `tests/test_rag_store.py`.

- **Topic stagnation detector (K18)** — Sibling of K6 that fires on the *inverse* signal: when the rolling per-turn distance to the K6 centroid stays low across a window (default 6 turns), Aiko gets a "Heads-up: you've been circling the same topic with Jacob for a bit" / "Heads-up: this thread has been pretty looped for a while" cue and is nudged toward a soft pivot, deepening, or a real off-ramp. Implemented as [`TopicStagnationDetector`](../app/core/conversation/topic_stagnation.py) — a pure streak counter with no embedder, no rag_store, no per-user state — that consumes `NoveltyDetector.last_distance` directly so there is zero extra embedding cost. Bands the rolling mean: `mean < stagnation_strong_threshold=0.10` → `strong_lull`, `mean < stagnation_mild_threshold=0.18` → `mild_lull`, otherwise silent. Three suppression gates keep the cue rare: warmup until the deque is full, `stagnation_cooldown_turns=4` after each fire (longer than K6's because lulls are by nature drawn-out), and a `stagnation_post_novelty_suppression_turns=3` window right after K6 fires so a fresh topic shift doesn't immediately read as "we've been on this for a while". A `distance=None` from K6 (short text / warmup / embed failure) is treated as no measurement and does not advance the streak. Surfaces through a new `stagnation` inner-life provider on [`PromptAssembler`](../app/core/session/prompt_assembler.py) registered *after* K6's `novelty` provider so the K18 detector reads K6's just-populated `last_distance`/`last_band`; the rendered block lands in the system prompt immediately after `novelty_block`, clustering both reaction cues together. Persona guidance lives in the "Same topic for a while" block of [`aiko_companion.txt`](../data/persona/aiko_companion.txt) and explicitly tells Aiko the *absence* of the cue is also a signal — a focused conversation is fine. Settings: `agent.topic_stagnation_enabled` (master switch) plus the five `memory.stagnation_*` knobs. **MCP-debuggable**: the detector logs one INFO line per scoring turn — `topic-stagnation: mean=%.3f band=%s window=%d` — grep-friendly via `tail_logs(module_contains="topic_stagnation")`. To repro a hit end-to-end: send 8–10 messages on a single narrow topic (e.g. all about debugging the same bug), watch the rolling mean drop in the log, then `band=mild_lull` then `strong_lull`; send one off-topic message and the post-novelty suppression silences K18 for the configured window. Tests: `tests/test_topic_stagnation.py`, plus K18 hooks added to `tests/test_novelty_detector.py` (`last_distance`/`last_band` exposure) and a stagnation provider-slot block in `tests/test_prompt_assembler.py`.

- **LLM client layer (the transport under the routes)** — the config side is the bullet above; this is what actually speaks to a provider. A structural [`ChatClient`](../app/llm/chat_client.py) Protocol (shared `ChatResponse` / `ChatToolCall` / `ChatUsage` dataclasses + `strip_thinking_blocks`) backs two concrete clients: [`OllamaClient`](../app/llm/ollama_client.py) and [`OpenAICompatibleClient`](../app/llm/openai_compatible_client.py). API-key resolution is `provider.api_key` (hydrated from the OS keychain by `secret_store`) → the env var named by `provider.api_key_env` → a per-host hint in `_PROVIDER_ENV_HINTS` (e.g. `GEMINI_API_KEY` for `generativelanguage.googleapis.com`). `SessionController` holds `self._chat_client` (TurnRunner + ProactiveDirector) and `self._worker_client` (every background worker — reflection, dream, beliefs, conflicts, curiosity, …, ~24 init sites) side by side; the two collapse onto one cached instance when both routes name the same provider. `self._ollama` is a back-compat alias for `self._worker_client` — new code should use the explicit name. Keeping `worker_default` on `local_ollama` while `main_chat` is remote is now just a routing choice, not a flag. Hot-reload runs through `update_route` → `_rebuild_llm_clients`, which mutates the gated worker proxies in place so the ~24 holders follow without being rebuilt, then pushes the new client to `TurnRunner` / `ProactiveDirector` via `update_runtime(client=…)`. - **Self-disclosure / vulnerability budget (K15)** — Aiko emits `[[remember:self:...]]` tags for personal notes (taste / admission / softness). Without pacing, the cheapest LLM path is dropping tier-3 disclosures every other turn — that reads as oversharing in-session and cardboard intimacy across days. K15 adds a soft, wall-clock-driven token bucket that paces *how often* a personal note lands. Pure module [`app/core/affect/vulnerability_budget.py`](../app/core/affect/vulnerability_budget.py) owns the math: `BudgetState{spent, last_decay_at}` dataclass + `classify_disclosure_tier` heuristic (priority ladder: Aiko's `tier=N:` self-tag fast-path -> tier-3 marker patterns -> tier-2 marker patterns -> length-based lift >= 100 chars -> default tier 1), with `tier_cost(tier)` mapping to 1 / 3 / 6 tokens by default. Capacity is `compute_capacity(closeness, trust)` — linear interp over `(closeness+trust)/2` from `[-1, 1]` to `[min_cap=1, max_cap=12]`, both axes sourced from [`RelationshipAxesStore`](../app/core/relationship/relationship_axes.py); a brand-new user with no relationship state defaults to neutral -> midpoint capacity ~6. Bucket regenerates over wall-clock hours (`apply_decay`: `new_spent = max(0, spent - regen_per_hour * elapsed_h)`, default `0.5 tokens/hour` so a tier-3 spend recovers in ~12h and a full capacity bucket in ~24h). Storage is **on `kv_meta`** — one JSON key `aiko.vulnerability_budget` carrying `{spent, last_decay_at}`, same `aiko.*` namespace as K27. **Soft enforcement only**: the provider's rendered cue is the *only* mechanism — never suppresses the underlying memory write, never filters reply text, never caps the spend at capacity (going over produces a *stronger* cue next turn). [`InnerLifeProvidersMixin._render_vulnerability_budget_block`](../app/core/session/inner_life_providers_mixin.py) reads + decays + persists-back + renders on every turn; four cue shapes (half-spent / at-cap / over-cap / **low-ceiling override** when `capacity <= 2` AND `spent > 0`). Persona block ("Sharing yourself" in [`aiko_companion.txt`](../data/persona/aiko_companion.txt)) teaches Aiko the four cue shapes + the explicit override clause ("if something he says lands somewhere real for you, you're allowed to meet it -- you're not a budget calculator"). MCP-debuggable: `get_vulnerability_budget_state` (master switch, `spent` / `last_decay_at`, live `closeness` / `trust`, computed `capacity` + `ratio`, the **predicted cue that would render right now** as `cue_preview`, full settings snapshot of all 7 knobs, force-flag state); `spend_vulnerability(tier)` mirrors the post-turn hook for one tier without a real LLM turn (validates `tier in {1,2,3}`); `reset_vulnerability_budget()` arms `_vulnerability_budget_force_reset` for a one-shot kv wipe. Settings: 7 new `AgentSettings` fields (`vulnerability_budget_enabled` / `_min_capacity` / `_max_capacity` / `_regen_per_hour` / `_tier1_cost` / `_tier2_cost` / `_tier3_cost`) with documented floor clamps. - **Brain Orchestration Phase 2 — scaling foundations (schema v17)** — Phase 2 layers four new top-level concepts on top of the phase-1 `BrainEventQueue` / `BrainLoop` / `tasks` table without breaking any wire-level contract. (1) An **append-only task event log** ([`task_events`](../app/core/tasks/task_events.py) table + [`TaskEventStore`](../app/core/tasks/task_events.py) with 11 stable `EVENT_*` constants — `started`, `progress`, `phase_change`, `input_question`, `input_answer`, `completed`, `failed`, `cancelled`, `interrupted`, `heartbeat_stalled`, `child_spawned`) records every meaningful lifecycle moment + handler-defined custom events via the new `TaskEventEmit(type, data)` outcome. (2) A **dedicated input/answer history** ([`task_inputs`](../app/core/tasks/task_inputs.py) table + [`TaskInputStore`](../app/core/tasks/task_inputs.py) with four status constants — `pending`, `answered`, `superseded`, `cancelled`) unblocks multi-clarification flows ("which folder?" → "which file?" → "which line?") — the orchestrator calls `supersede_pending_for_task` before every fresh `TaskInputNeeded` so no orphan `pending` row leaks. The phase-1 single-slot `tasks.input_request` is still kept in sync as a denormalised "what's the current question?" mirror for cheap WS / REST reads. (3) **`phase` / `parent_task_id` / `heartbeat_at` as first-class `tasks` columns** — `phase` is the human-readable label (`"extracting_prices"`) the LLM and the TasksTab read instead of trying to make `progress=0.42` meaningful for a discrete state machine; `parent_task_id` records spawn relationships as a single-parent tree (NOT a DAG — keep it simple) so cancel-cascade and the future "wait on all children" feature can both walk it; `heartbeat_at` is bumped on every emit so a daemon thread can flag "running but silent for 5 minutes" without false positives. (4) **Heartbeat sweep + cleanup worker — two independent daemons.** [`HeartbeatChecker`](../app/core/tasks/task_heartbeat.py) is a `daemon=True` thread that wakes every `task_heartbeat_check_interval_seconds=30` (floor `5`, set to `0` to disable) and calls `TaskStore.list_stalled` for `running` rows older than `task_stalled_seconds=300` (floor `60`); action `warn` (default) just logs + appends `EVENT_HEARTBEAT_STALLED`, action `fail` also flips to `status='failed'`, action `disabled` is the kill switch. `awaiting_input` / `paused` are never flagged — they're stalled *by design*. [`TaskCleanupWorker`](../app/core/tasks/task_cleanup_worker.py) is a regular `IdleWorker` that runs in quiet windows, deletes terminal rows older than `task_cleanup_retention_days=30` (floor `1`, capped by `task_cleanup_max_rows_per_tick`), and cascade-deletes the matching `task_events` + `task_inputs` rows in order. `TaskOrchestrator.cancel(task_id)` also walks `parent_task_id` children depth-first when `task_cascade_cancel_children=true` (default), appending `EVENT_CANCELLED` with `data={"by_cascade": true}` on every descendant. **REST**: `GET /api/tasks/{id}/events?limit=&offset=&type=` (paginated chronological log) and `GET /api/tasks/{id}/inputs` (full input history including superseded/cancelled rows); `GET /api/tasks/{id}` now includes `phase` / `parent_task_id` / `heartbeat_at`. **WS**: `task_progress` payloads now carry `phase` when present. **Frontend**: `TaskStrip.tsx`'s `TaskChip` renders `phase` next to the status; `TasksTab.tsx` adds a lazy `EventsExpander` per row so a 10K-task history doesn't materialise upfront. **Six new agent settings** (defaults / floors): `task_heartbeat_check_interval_seconds=30/5`, `task_stalled_seconds=300/60`, `task_stalled_action="warn"` (unknown values fall back to `warn`), `task_cascade_cancel_children=true`, `task_cleanup_retention_days=30/1`, `task_cleanup_interval_seconds=21600/600`. **MCP debug surface**: `get_heartbeat_state()`, `force_heartbeat_sweep()`, `force_run_idle_worker("task_cleanup")`, `list_task_events(task_id)`, `list_task_inputs(task_id)`, `emit_task_event(task_id, type, data)`. **Recovery interaction**: `recover_interrupted_tasks` now also calls `cancel_pending_for_task` on every row demoted from `running` to `interrupted` so the user never sees a pending question for a task they thought was done; `awaiting_input` rows are preserved as-is (pending input stays valid).

## Code Conventions

- Python 3.11+, dataclasses + slots for settings, FastAPI for the HTTP/WebSocket layer.
- LLM calls go through `app/llm/ollama_client.py` (`chat`, `chat_stream`, `chat_with_tools`). Tool dispatch happens in `app/core/session/turn_runner.py` via a pre-stream `chat_with_tools` pass; the streaming reply runs immediately after.
- The agent's available tools are built once per turn from `config.tools` by `SessionController.rebuild_tool_registry()` — see `app/llm/tools/builtins.py` for the live set (`get_time`, `recall`, `web_search`). Other gated tool families: world tools (`tools.world`), and the H11 weather tools `get_weather` / `get_forecast` (`tools.weather`, see [`app/llm/tools/weather.py`](../app/llm/tools/weather.py) and [`docs/weather-sync.md`](../docs/weather-sync.md)).
- TTS text processing (`prepare_tts_text` in `app/core/session/session_text_utils.py`) applies only to the spoken stream, not the chat transcript. **It must be self-sufficient: never assume `sanitize_assistant_text` ran first.** They clean two different copies of the text at two different points in the turn — the streaming voice path in `TurnRunner` feeds `prepare_tts_text` raw model deltas sentence by sentence, while `sanitize_assistant_text` only touches the copy that gets persisted, which happens after the audio has already played. (The proactive paths *do* sanitise first, so the two look interchangeable until you check the main chat path.) That gap is why emoticons were audible for a long time despite the sanitiser having stripped them since forever: `:P` was clean in the transcript and spoken as a letter "P". **Emoticons are now a spoken-side-only cleanup** — `_EMOTICON_RE` / `_EMOJI_RE` are applied by `prepare_tts_text` alone, and the transcript keeps whatever face she wrote. Banning them on both sides (sanitiser *and* a persona rule) backfired: fighting the ban, she emitted broken halves, and a swallowed `:3` reached the transcript as a bare `3` in "my hug has done its job, 3". Suppressing a model's output habit at the last mile tends to produce mangled output rather than none, so prefer letting it through and filtering only the consumer that actually breaks — here, the synthesiser. (Pictographs still never reach the transcript, but that's the ASCII-only filter, not an emoticon decision.) Rule of thumb: the transcript wants text that *reads* well (dashes stay), the spoken stream wants text that *sounds* right (dashes become spaces, hyphenated compounds split, numeric ranges become "to"), so divergence between the two is intended — mirror a cleanup into both rather than moving it. **On the transcript side the distinction that matters is hyphen vs. dash:** `sanitize_assistant_text` is ASCII-only downstream, so a unicode dash must be substituted or it disappears mid-sentence, and mapping em/en dashes onto a bare `-` rendered "Yes—that" as "Yes-that", which reads as a typo. U+2010/U+2011 are *hyphens* (word joiners) and stay glued; U+2012–U+2015 and U+2212 are *dash punctuation* and become a spaced `-`. The spoken side keeps deleting all of them regardless — this only makes the bubble readable. **When something audible isn't in the transcript, check the synthesiser before the text pipeline.** A stray syllable at the end of spoken chunks looked exactly like a leaked meta tag and was not one: `INFO app.turn_runner` logs the `llm raw response:` verbatim, which showed clean text, and replaying it through `safe_visible_prefix` → `drain_tts_stream_chunks` → `prepare_tts_text` at several delta granularities reproduced the chunking exactly. The cause was Pocket-TTS decoding 240 ms past end-of-sequence (`tts.pocket_tts_frames_after_eos`, see [configuration.md](../docs/configuration.md)). Text-shaped symptoms are not always text bugs, and the raw-response log line is the cheapest way to tell the two apart.
- SQLite (`data/chat_sessions.db`) is the source of truth; LanceDB (`data/lancedb/`) mirrors `memories`, asynchronously indexes `messages`, and holds chunked uploaded `documents`.
- Inline tags Aiko emits: `[[reaction:...]]` (mood label, drives Live2D expression and TTS reaction-to-speed); `[[remember:...]]` / `[[remember:self:...]]` (writes a long-term memory); `[[arc:...]]` (H1 conversation-arc self-tag — one of `casual_check_in / support / planning / reflection / playful / silly`, lands at confidence `0.85` on the regex 0.5 < self-tag 0.85 < smoother 0.95 ladder, see [`app/core/conversation/conversation_arc.py`](../app/core/conversation/conversation_arc.py)); and `[[prosody:...]]` (per-sentence vocal delivery — one of `whisper / soft / slow / fast / firm`, orthogonal to the reaction mood label, applies to the single sentence that opens with the tag, see [`app/core/voice/cadence.py`](../app/core/voice/cadence.py)). All four are stripped from the spoken/chat output before TTS / transcript persistence. Stage-direction earcons (`[[laugh]] [[sigh]] [[gasp]] [[hum]] [[tsk]] [[chuckle]] [[soft_sigh]] [[sharp_gasp]] [[breath]] [[mm]]`) are also inline tags but route through a side-channel earcon player rather than TTS.
- Persona file at [`data/persona/aiko_companion.txt`](../data/persona/aiko_companion.txt) is user-editable, and everything in it is always-on prompt text — the one category that is *not* (conditional handling notes, keyed to the prompt block that triggers them) was moved out to [`conditional_handling.txt`](../data/persona/conditional_handling.txt) beside it precisely so the persona file reads as what it is. See [`docs/cue-pool.md`](../docs/cue-pool.md#the-persona-hoist) before adding a "when your context says X…" section to either. **Quoted strings in the persona are two different things and must not be edited as one class:** *example utterances* (what Aiko should say) versus *literal context formats* she is being taught to read, which are emitted verbatim by code — `"Your day's colour today: <name> -- <short reason>."` ([`day_color.py`](../app/core/affect/day_color.py)), `"(was planned for … -- should be done by now)"` ([`timephrase.py`](../app/core/infra/timephrase.py)), the implicit-need cues, the finished-task preamble. A style sweep over the persona (the dash ban, for instance) must skip those or the file starts describing a format that no longer exists. Style rules also need their examples fixed in the same pass: an instruction contradicted by twenty in-character demonstrations of the banned thing is mostly decorative. The "Reading {user_name}" section instructs Aiko to mirror the user's register from the live `vocal_tone` and `user_state` prompt cues. The same nudge is mirrored in `_SPEECH_GRAMMAR_ADDENDUM` ([`app/core/session/prompt_assembler.py`](../app/core/session/prompt_assembler.py)) so a deleted/rewritten persona file doesn't lose the behaviour. **Every "Jacob" in the persona has been templated** as the literal placeholder `{user_name}` (Phase 4d). `PromptAssembler._load_persona()` calls `.format(user_name=resolve_user_display_name(...))` once per load; new persona text must keep all braces as `{user_name}` (any other `{...}` token crashes `.format()` and falls back to the raw text via the try/except guard). The legacy backup file `aiko_companion_backup.txt` was deleted — never restore it. **Tool source-of-truth split**: the persona does NOT carry a per-tool catalogue. Every agent tool is already passed to the model natively via the `tools=` parameter (`TurnRunner` -> `chat_with_tools`), and each tool's `schema()` description ([`app/llm/tools/*.py`](../app/llm/tools/) — `builtins`, `world`, `goals`, `file_tasks`) is the imperative, self-contained "what this tool does / when to call it / sync vs async" reference. The persona's "How tools work" block only describes cross-cutting *handling* rules (sync returns inline, async returns a task id whose result lands a later turn, the anti-deferral rule, ask-back-on-disambiguation, never paste raw output). **When adding a tool, put the description in its `schema()` — do NOT re-document it in the persona.** The persona was trimmed ~47% (Phase: persona-trim-tool-budget) by removing this duplication and compressing each K-feature cue section to its essential anti-pattern; the literal `[[...]]` tag vocabulary Aiko must emit (reaction taxonomy, prosody values, `[[remember:...]]` / `[[gap:...]]` / `[[predict:...]]` / `[[arc:...]]` / `[[goal:...]]` / `[[touch:...]]` / `[[conflict:...]]`) was preserved verbatim.
- **Surfacing-conduct self-model (L42, consuming L37/L38)** — [`surfacing_conduct.py`](../app/core/concepts/surfacing_conduct.py) detects weekly, relationship-scoped **concentration**, **neglect**, and **fixation**. Concentration normalizes cluster surfacing against bounded, already-indexed user-message vectors; neglect excludes T0 profile claims and existing `conduct` concepts; fixation reads only `flex` / `activation` ledger lanes, excludes core kinds, requires a frequency outlier, and compares reception with L38's relationship baseline. Findings become relevance-only, moderately plastic `subject="aiko", kind="conduct"` concepts; the bounded KV snapshot is only for behavioral consumers. Concentration/fixation suppress K81 taste-lean; neglect does **not** bias curiosity until L42b has real-data evidence. The rare T6 notice requires lull + relationship warmth + one-per-conversation + weekly persisted cooldown, is dropped under aggressive assembly, and must speak as a fallible relationship observation — **never expose counts, rates, tracking, prompts, scores, or machinery**.
- **Concept evolution (L17b/c/e, schema v31)** — How a belief changed and why, kept permanently. **The one invariant to not break: the [`ConceptDriftWorker`](../app/core/concepts/concept_drift_worker.py) is the single writer of `label` / `rationale`, exactly as L3 is the single writer of `confidence` / `plasticity` / `status`.** Labels used to be frozen at synthesis (`_reinforce` attached evidence and left the wording alone), so the backlog's headline "relabel" shape could never fire; now [`concept_synthesis_worker.py`](../app/core/concepts/concept_synthesis_worker.py) *stages* a better wording as a `relabel_proposed` event (no schema change — `event_type` is an open enum, so a new event kind is a value, not a migration) and the worker adjudicates it off-turn behind cheap gates: normalized materiality (case/punctuation/filler/plural-stemmed, min token delta), a cosine floor at the dedupe bar against the *current* label so a genuinely different belief stays a separate concept, per-concept cooldown, per-run cap, shared `FactCheckRateLimiter`, then a narrow "is B a better wording of the same belief" adjudication with a negative cache. **History is its own thrash guard** — any label the concept previously held is refused, read straight from the `label` snapshots already in `concept_events`, so a phrasing ping-pong dies after one round trip for free. The pure classifier [`concept_drift.py`](../app/core/concepts/concept_drift.py) (no store, no worker deps) makes **succession the primary shape**, not a secondary one: because relabelling only just became possible, most real evolution shows up as a new concept forming *below* the `_DEDUPE_COS = 0.86` bar while the old one fades, paired on label cosine in the band below that bar + evidence overlap + temporal anti-correlation; emergence / loss / revival / confirmed relabel are secondary and confidence-only movement is noise. Salience is plasticity-weighted, so movement in a sticky belief outranks the same movement in a `taste` or L42 `conduct` row. Two schema additions, both append-only and never pruned: `concept_learning_events` (old/new endpoints, shape, salience, trigger event ids, mediators, evidence ids **and labels snapshotted at detection time** so the record survives the rows it cites, natural-language *because*, deterministic fingerprint for idempotency) and `concept_aliases` (absorbed → canonical, written inside `merge_into` **before** `delete(abs_id)` — the last moment the absorbed row exists; without it every history ending in a merge was unreachable, since only free text in the `merged` reason connected the two). Reads: `ConceptEventStore.drift_window` is a **two-ended** trajectory (oldest anchor + newest movement), because `trajectory()`'s oldest-first `LIMIT` protects a concept's origin but lets L17a `confidence_sample` rows bury every recent move. **The crash lesson is structural here:** `demand()` compares a KV watermark against `MAX(id)` of `concept_events` and nothing else — no NumPy, no store scan — and all pairing happens in `run()` over one `ConceptStore.matrix_snapshot()` matrix with a single matmul, never per-concept `nearest()` (whose `_filtered_matrix` fallback restacks a fresh matrix per call, the exact shape that caused the `ConceptConsolidationWorker.demand()` access violation). Debug surface: `GET /api/concepts/learning` / `{id}/provenance` / `drift` (+ `drift/run`), the `get_concept_learning` / `get_concept_provenance` / `get_concept_drift_state` / `force_concept_drift` MCP tools, and Settings → Memory → **Evolution** — keep L26's "why did this enter the current prompt" distinct from L17e's "how did this belief evolve". The **only** conversational surface is the T6 `concept_learning_block` ([`inner_life_part3.py`](../app/core/session/inner_life_part3.py)), which reads solely the worker's bounded KV pending snapshot (no turn-path scan / embedding / LLM call) behind trust + warmth + salience + lull-or-live-relevance + once-per-conversation + per-change watermark + a long persisted global cooldown; the model gets old, new, and *because* and **never** scores, ids, shapes, or event types, and is told to state a fallible first-person shift rather than ask whether it's right (which would spend K47's question budget on reassurance-seeking). Deliberately not built here: L31 fission (the classifier may reserve the shape but must not infer splits without the missing structural primitive); the three consumers built on top of this record are the next bullet. See [`docs/concept-lifecycle.md`](../docs/concept-lifecycle.md#concept-evolution-l17).
- **What a concept may accept as evidence (L31)** — Creation is gated by each kind's `min_sources` / `min_chain` / `directional` bars; *reinforcement* was not gated at all, so `_reinforce` attached every source the LLM cited on the strength of the id appearing in the list of 40 it was shown. [`concept_evidence_admission.py`](../app/core/concepts/concept_evidence_admission.py) is the one bar, sized and sited like `concept_dedupe.py` for the same reason, and `ConceptSynthesisWorker._reinforce` is the single choke point both reinforce paths funnel through. **Two bars, because neither catches the other, and both defaults are measured:** `concept_evidence_admission_cosine` (0.35, refuses 2.2% of the 6091 live evidence edges) stops *contamination* — the row citing "Jacob enjoyed Chainsaw Man's opening song" as evidence for deepening intimacy; `concept_evidence_max_sources` (24, the p99 of `distinct_source_count`) stops *accretion* — the vague ritual label that absorbed 145 of the graph's 158 `shared_moment` memories with nothing off-topic in it at all (its lowest evidence cosine is 0.385, above any usable floor). **The invariant to not break: a concept refused only because it hit the ceiling must still bump `last_reinforced_at`.** L3 reads that to decide a belief is still observed and L46's dormancy TTL retires by wall-clock silence, so a frozen clock would drift the row `active → dormant → retired` while its evidence kept arriving — deleting the best-supported beliefs *because* they had the most evidence. Off-topic refusal is the opposite and moves nothing, including the L17 relabel bid the same proposal carries. A source whose vector cannot be resolved is **admitted**: a `("cluster", rep)` node resolves through the rep's *memory* row, and failing closed would starve every concept the moment an embedding went missing or the embedding model was swapped. Forward-only by design — nothing trims an edge a concept already holds. L31's original *fission* shape was refuted by measurement before it was built (the detector cannot tell one concept's evidence from two concepts' pooled); the control numbers are in [`shipped/concepts.md`](../docs/personality-backlog/shipped/concepts.md#l31-evidence-admission-control----what-a-concept-may-accept).
- **Reading the learning record: the diary, the autobiography, the self-correction rules (L17f / L19 / L17d, schema v32)** — Three consumers of `concept_learning_events`, plus the bug that had to be fixed before any of them could be validated. **The bug, and the lesson:** `ConceptDriftWorker.run()` advanced the event watermark to the global `MAX(id)` even though `_run_classification_pass` had only examined the lowest `concept_drift_max_concepts` concept ids, so five weeks of history was skipped and then marked processed — invisible until something tried to *read* it. The fix is a **second cursor that pages by concept id** (`concepts_with_events_after(after_concept_id=…)` + `_run_sweep_pass`, running after the forward passes with `since_event_id=0`, idempotent via the existing fingerprint UNIQUE, done-sentinel when a page comes back empty). **Any bounded pass that advances a global watermark has this shape of bug; check for it before adding another.** (1) **L17f diary** — [`evolution_diary_store.py`](../app/core/concepts/evolution_diary_store.py) + [`evolution_diary_worker.py`](../app/core/concepts/evolution_diary_worker.py), the `evolution_diary` table (v32), deliberately **not** the H9 `memories.kind="diary"` log (that one is subjective journalling; this is a grounded change log with provenance). One short first-person paragraph per period, composed **only** from stored `because` prose; a period below `evolution_diary_min_events` writes nothing *and leaves its events pending*, so thin weeks accumulate rather than producing filler; the cooldown is spent even on an empty composition so an unproductive period cannot loop. The forward cursor it needed is reusable: `ConceptLearningEventStore.list(after_id=…)`, `count_since` (one aggregate for `demand()`), and `page_since` — **oldest id first, deliberately**, because taking the newest page would advance the watermark past unread older events, which is history lost rather than deferred. **Two numbers, never one (H15).** `DriftFinding.evidence` is shape-neutral and is the *only* thing allowed to gate detection; `salience` is `evidence` times a per-shape narrative prior (`concept_drift._SHAPE_BASE`) and may only ever order narration. They used to be the same field, so a prior about which kinds of change are interesting was silently deciding which changes were *real* — a belief forming was held to twice the bar of a belief being reworded, and the diary, whose whole subject is how her understanding changed, could narrate a formation in 1 of 276 events it cited. If you add a shape, set its base by how much it is worth telling and nothing else. Page selection is likewise per shape (`select_page`): `succession` is ~79% of arrivals and may take at most half a *contested* page, backfilling rather than truncating so a quiet period is still narrated in full. It stays on a contiguous run so the watermark is still the page's own high-water mark — a rewording the cap passed over *below* that mark is consumed on purpose, and anything above it is simply read again next tick. (2) **L19 autobiography** — [`self_history.py`](../app/core/concepts/self_history.py) builds eras of classified change (flipped / faded / revived / born / settled) over **all** concepts including retired ones, read via the `recall_self_history` tool, `GET /api/concepts/self-history`, MCP `get_self_history`, and Settings → Memory → **Story** (the same payload the model gets, so what she *would* say is inspectable first). Grounding is enforced **in the builder, not the prompt**: every entry carries its concept and learning-event ids, and `thin_record` obliges her to say she has no record rather than invent a past — `settled` beliefs don't count toward a record being substantive. Read cost is flat in concept count: aliases and learning events are each read **once** in bulk and grouped in Python, because a per-concept query on a tool-call path is hundreds of round trips. (3) **L17d self-correction** — [`self_correction.py`](../app/core/concepts/self_correction.py) (pure, numpy-only) single-links the `because` clauses, and [`proposers/self_correction_aiko.py`](../app/core/concepts/proposers/self_correction_aiko.py) names the habit as an actionable rule. It lands as `communication_style` / `subject="aiko"` / `evidence_model="meta"` rather than a new kind, precisely so it inherits that kind's live T3 steering path — the point of the feature is that a rule she learned about herself *changes her behaviour*. **Two gates are load-bearing:** the evidence floor counts distinct **beliefs**, not events (three corrections to one belief is her wobbling on one thing), and `concept_self_correction_cooldown_days` outlasts fresh history so she cannot rewrite her strategy weekly. It also required inverting one L12 meta rail: "a meta whose bases aren't all `active` is moot" would make every self-correction permanently moot, since its bases are the beliefs she *stopped* holding — so the arity rule is now declarative, `ConceptKind.meta_min_active_bases` (`None` = all / tension, `2` = generalization, `0` = bases are history), read by the L3 worker instead of branching on kind names. **Note the namespace collision:** `agent.self_correction_enabled` and `memory.self_correction_*` belong to K38's in-reply "I got that wrong" cue; everything here is prefixed `concept_self_correction_*`. Settings for all three are in [`docs/configuration.md`](../docs/configuration.md).
- **The fade invariant, and dating a change (L22 hygiene)** — Two rules that keep the L17/L19 story honest under *bulk* graph maintenance, learned by running the L22 sweep (293 concepts parked in one transaction) and the decay retune (`concept_confidence_halflife_days` 45 → 7.5) into a live pipeline. **(1) A belief she never held cannot be lost.** `classify_trajectory` drops a `loss` finding when `not trace.ever_reinforced` (`ConceptTrace.promoted_at` / `last_reinforced_at`, read off the concept row so a reinforcement outside the bounded event window still counts), and `self_history._classify` returns an empty `change` — meaning **omit from the arc entirely** — for a faded status with no recorded `loss` learning event. Both halves are needed: the write side stops the events being minted, the read side stops status alone being narrated. Succession is **deliberately exempt** on both sides (a fade matched to a semantically-near rising replacement is its own evidence the belief was real); emergence and revival need fresh evidence to occur, so they were already safe. **(2) A learning event is dated when the change happened, not when it was noticed** — `DriftFinding.occurred_at` (the decisive event's timestamp; for a succession specifically **the rise**, since the belief changed when the replacement took over rather than when the loser's status caught up), which `LearningEvent.from_finding` writes as `created_at`. Without it the cold-start backfill filed five weeks of history under one afternoon, and any bulk status pass could stamp a graph's worth of revisions with a single date. Anything that reads a batch of learning events must therefore take min/max over `created_at` rather than trusting page order (see the diary's `period_start` / `period_end`). **Before adding any bulk lifecycle action, ask what it makes her believe she learned.**
- **Concept importance — the second strength axis (L32)** — `confidence` answers "how likely is this true"; [`concept_importance.py`](../app/core/concepts/concept_importance.py) answers "how much does it matter", in `[0, 1]`. Four invariants, in the order they are easiest to break. **(1) Derived, never stored.** It is a pure function of `ConceptKind.importance` (the per-kind stakes prior: `boundary` 0.9 → `taste` 0.3) and the emotional charge of the topic clusters the concept is grounded in. There is no column, no writer, and therefore no decay policy — it moves when its inputs move. Do not "just persist it for speed"; that reintroduces every question the derivation dissolved (a second writer racing L3, a plasticity interaction, and "what lowers importance?"). **(2) Affect only ever lifts.** `blend_importance` is `prior + (1 - prior) * lift * charge`, monotonic and never below the prior, because ~46% of the live graph grounds on no affect-bearing cluster — a symmetric blend would read "no data" as "trivial" and penalise the majority. Same convention as `recency_boost` returning a neutral `1.0` on a missing timestamp. The charge itself is `abs(valence) * (0.5 + 0.5 * arousal)`: **valence magnitude is the stakes signal and arousal only scales it**, so a neutral-but-agitated topic contributes nothing while a strongly-felt quiet one keeps half its charge. **(3) T3 only — never `_stable_rank`.** Importance reaches the `relevant_context` scorer and nothing else. [`concept_view.py`](../app/core/concepts/concept_view.py) ranks the T0 `profile_block` lane on *quantised* confidence with a `concept_id` tie-break specifically so per-tick drift cannot reorder bullets and break the prompt-cache prefix; a live affect-sensitive term there puts that churn straight back. Guarded by an ordering assertion *and* a source check that `concept_view` never imports the module (`test_concept_view.StableRankTests`). **(4) A multiplier, not a seventh weight.** `surface_score` applies `1 + strength * (importance - 0.5)` beside habituation. Neutral importance and `concept_importance_strength=0.0` are both byte-exact no-ops. For the same reason it is **not** a `surface_reason` candidate: a multiplier scales every term equally, so it never wins a contest — it is reported as its own trace fields (`importance` / `importance_prior` / `importance_charge`) instead. **The id bridge is the one place to get wrong quietly:** a `cluster` evidence edge stores the cluster's **representative memory id** in `src_id`, not a `cluster_id`, and the two spaces overlap only by accident — resolve it through the live topic graph's membership (`membership_from_clusters`), never by treating `src_id` as a cluster. Public seam for new consumers (L30a hypotheses, L30d zones): `SessionController.concept_importance_context(concepts)`, which is deliberately status-agnostic so a `candidate` scores like an `active` row.
- **The tentative register — surfacing what she hasn't settled (L30a)** — Every concept read path filters to `status="active"`, which *hides* a `candidate` rather than hedging it. [`ConceptView.hypotheses`](../app/core/concepts/concept_view.py) is the **only** exception, and the isolation is the whole safety story: a candidate reaching `core` / `core_lane` / `for_target` puts an unearned claim into the T0 `profile_block` and breaks the prompt-cache prefix at the same time (guarded per-lane plus structurally in `test_concept_view.TentativeRegisterIsolationTests`). **Selection cannot use confidence, and cannot use age — both are counter-intuitive and both were measured.** On a live 261-candidate graph the candidate pool's *median* confidence was **0.82** (the proposer's confidence says "is this well-formed?", not "is this established?"), and **144 of 261** candidates had cleared every evidence and confidence bar and were held back only by `concept_promote_min_age_days` (that count is against each row's *own* `promotion_gate`; the 238 originally recorded here was against the global `concept_promote_*` settings, which every shipped kind floors via `max` — measure with the kind's gate). So [`concept_hypothesis.py`](../app/core/concepts/concept_hypothesis.py)'s `unsettledness` reads distinct-source breadth and conviction *only* — **a belief waiting out a timer is not an open question**. Two floors, both load-bearing: `hypothesis_min_unsettled` (0.22) sits just above the **exactly 0.20** a twice-grounded, fully-confident belief scores, which is the pool's largest cluster; and `hypothesis_min_sources` (1) drops ungrounded proposals, which score *highest* on unsettledness precisely because nothing supports them — without it the lane leads with bare LLM hunches. Ranking is a **product** (`cosine * unsettled * importance_factor * habituation`) so every term can veto; a sum would let one strong signal carry a candidate in. **But the budget selector is handed plain cosine, not that product** — four sub-1.0 terms land on a different scale from every other source's relevance, so feeding it in would silently redefine `min_relevance` for this lane and skew the cross-source fill. Rendering needs its own function for the same reason selection does: `_hedge_for_confidence` tops out at 0.8, *below* the median candidate, so reusing `_render_relevant_concepts` would print an unproven hunch as "You're fairly sure" — `_render_hypothesis_concepts` and `_HYPOTHESIS_LEADS` stay strictly weaker. **The cross-lane dedup is not redundant** even though statuses are disjoint: `_last_profile_concept_ids` is a stash from a previous render that survives a slice-cache hit, so a concept L3 demotes in between would be asserted in T0 and wondered about in T3 in one assembly. Retrieval prerequisite: the store's active-only matrix cache was generalised to one per status, because `nearest(status="candidate")` otherwise falls through to `_filtered_matrix` and restacks a fresh array per call — the pattern behind the access violation that took down the consolidation worker's `demand()` probe.
- **Testing a hunch — the ask-and-learn loop (L30b/L30c)** — L30a lets Aiko *see* an open question; this closes one. Selection is [`ConceptView.testable`](../app/core/concepts/concept_view.py), which is `hypotheses` minus the rows an answer cannot move: **a candidate whose only unmet promotion leg is age is skipped**, because answering adds a *distinct source*, and 144 of 261 live candidates already clear sources and conviction and are only waiting out a clock. That leg is detected by re-running the concept's **own** `promotion_gate` with the age argument satisfied — never by comparing against `concept_promote_*`, since every shipped kind floors all three legs with its own constants via `max` (`identity` / `value` want three sources), so a global check is wrong for every kind at once. Ranking is `importance * unsettledness` with **no cosine term**: the [`ConceptHypothesisWorker`](../app/core/proactive/concept_hypothesis_worker.py) runs off-turn with no user text, and the *provider* applies the topical gate later. `concept_hypothesis` is the **only dual-mode cue**: the topic path fires on lexical overlap and does **not** set `_gap_cue_surfaced` (matching `knowledge_gap_notice` — riding a topic the user raised is not opening out of silence), and the gap path runs only if the topic path found nothing, defers to every other gap cue (it is **last** in `GAP_CUE_ORDER`), and adds a bar the topic path lacks, `concept_hypothesis_gap_min_importance`. Its `CueSpec` is deliberately **slot-less while still `gap_cue=True`**, so arming counts pool stock rather than the pending slot — most firings come from the topic path, and slot-based arming would under-count them. **K47 governs this block but not the L30a lane**: a musing costs the user nothing, an ask does; the lane's *invitation* to follow up is what the gate removes, and `_last_hypothesis_lane_concept_ids` stops one assembly both musing about and asking about the same belief. **[`answer_adjudicator.py`](../app/core/concepts/answer_adjudicator.py) returns four verdicts, and the fourth is the point**: *"not really, it's more that I hate being still"* is the most valuable reply a hunch can get, and `CORRECT` is what keeps a near-miss refinable instead of punishing it as false or cementing it as true. **The error costs are asymmetric, so the bars are** — a false confirm adds a source and promotes a wrong belief through L3's gate; a false deny costs re-earnable confidence. Confirming therefore requires positive LLM evidence, and every failure path (unparsed, exception, no client, off-subject) lands on `UNCLEAR`. `classify_pair` (F5) is a **one-way veto** — `definite` opposition downgrades a confirm, but its `no` means "found no opposition", never "agreed". **The write paths mirror existing writers** ([`hypothesis_resolution.py`](../app/core/concepts/hypothesis_resolution.py)): confirm is L2's `_reinforce` (evidence edge, counters **recounted** from `evidence_of` so a restated old fact cannot manufacture breadth, confidence and status untouched — L3 promotes through the ordinary gate); deny is L9's disproof (penalty **plus** the `contradicts` edge that makes it legible later); correct takes the penalty with **no** edge; unclear writes nothing. **This is the second sanctioned exception to "L3 is the single writer of `confidence`"**, after `UserCorrectionWorker._propagate_to_concepts` (F13) — the user contradicting a belief to Aiko's face is the same class of event as F13's demoted memory, and routing it through L3 would defer something the user just said out loud to a tick. `status` stays strictly L3's in both. `_resolve_concept_hypotheses` runs **immediately before** `_settle_awaiting_cues` and drives every awaiting row to a terminal state itself, because generic stage B reads topical overlap and would score a flat denial as a satisfied question. `max_asks=1`, and reaching `awaiting` spends it, so an unanswered hunch is dropped rather than re-asked. The three new `ConceptEvent` types are **not** in `STRUCTURAL_EVENTS`: `_shape_for` maps only shapes it knows, so an unmappable member returns no finding *and* masks the real structural event behind it — they reach the diary via the drift worker re-reading the concept instead.
- **Inventing a hypothesis — the forward direction (L30 Phase B, schema v34)** — Everything else in the concept stack runs *backwards* from evidence, so it cannot produce a thought Aiko was never given the material for. [`hypothesis_proposer_worker.py`](../app/core/proactive/hypothesis_proposer_worker.py) runs forwards: it speculates, files the guess to its **own table**, and the L30b/L30c loop tests it. **The invariant the whole layer rests on: an invention lives in `hypotheses`, never in `concepts`, until it graduates.** A `speculative` concept status was the obvious alternative and is the wrong one — every concept read path filters on `status`, and one missed filter puts a made-up sentence into the T0 `profile_block` as something Aiko asserts; a separate table makes that impossible instead of unlikely (guarded by `test_hypothesis_graduation.IsolationTests` + `test_hypothesis_store`). **`credence` is not `confidence`** and nothing may map one onto the other: confidence is *derived* from evidence and re-derived by L3 every tick, credence is *asserted* by the proposer and never recomputed by anything. That single fact generates every asymmetry with the concept side — a denied concept loses conviction and keeps living because L3 will re-read its evidence, a denied hypothesis **closes outright** because nothing will ever look at it again (and is kept as a row precisely so the novelty gate cannot re-invent it). `hypothesis_lane.InventedRow` reports `confidence=0.0` / `distinct_source_count=0` rather than translating; a caller wanting those from an invention is asking a question with no honest answer. **Two novelty gates, asymmetric on purpose**: `hypothesis_min_novelty` (0.88, *above* the dedupe bar) rejects re-inventing an existing guess, because over-rejecting here makes the layer sterile and the cost of a near-neighbour is one wasted row; `hypothesis_concept_novelty` (0.82, stricter) rejects speculating about something she already believes, because that failure is Aiko visibly forgetting what she knows. **The duplicate race is the normal case, not an edge case**: a confirmation stores the answer as an ordinary memory, L2 clusters it and proposes a concept knowing nothing about the hypothesis, and L2 needs one confirmation where graduation needs two — so `link_if_duplicate` runs after **every** confirmation (earliest possible stamp of `linked_concept_id`), a linked row goes quiet in the lane, and graduation takes the **merged** exit rather than forking a near-twin. That lookup passes `kind=None` (across kinds within the subject) because the proposer's guessed kind carries no authority and filtering on it would fork the graph on a taxonomy disagreement, and it matches `retired` / `dormant` rows because a belief she used to hold is still the same belief. Three exits, and `merged` is deliberately distinct from `graduated` so L17f/L19 can narrate "right about something I already knew" differently from "right about something new"; a `world`-subject guess has no concept kind to become and exits as a durable `fact` memory instead. **Graduation mints a `candidate` at the default confidence** and sets neither confidence nor status — being guessed right twice is not evidence beyond the two answers, which are already attached as edges for L3 to count. One dedupe bar for both entry paths ([`concept_dedupe.py`](../app/core/concepts/concept_dedupe.py)), extracted from L2 when this became the second caller, because two independently-tuned thresholds would agree for months and then silently diverge. Lane cap is 2 with **one per origin**, applied *before* the context budget: L32 importance blends a kind prior with the charge of grounded clusters, an invention has no grounded memories, so competing on score alone would bury it every time. **Two reads, deliberate inverses.** [`hypothesis_debug_mixin.py`](../app/core/session/hypothesis_debug_mixin.py) holds both: `open_hypotheses` (Aiko-facing, live and unlinked only — she should not muse about a finished guess or one a concept already speaks for) and `hypothesis_shelf` (the debug read behind Settings → Memory → Hypotheses — every status, linked rows included, full lifecycle). The hidden rows are exactly the ones that explain a silent lane, so neither read is a subset of the other by accident. Its write button `force_hypothesis_verdict` routes through the **live** `_apply_invented_answer`; never reimplement the credence math for a debug path, or it will drift and start lying about the real one. A forced confirm requires answer text, because a graduated concept's evidence edges are built from `answer_memory_ids` and a text-free confirm would mint a concept resting on nothing. Two related invariants: `delete_concept` must call `HypothesisStore.unlink_concept` (a linked row is hidden everywhere and `link_if_duplicate` only self-heals on the *next confirmation*, which such a row can never get — so it would hold a slot on a twelve-slot shelf forever), and `_nearest_hypothesis` blocks on every status **except `expired`** (an expiry is Aiko's own inattention, not evidence about the guess, and blocking on it retires that ground permanently). Canonical reference, including the full lifecycle diagram, the settings table and the debugging ladder: [`docs/hypotheses.md`](../docs/hypotheses.md).
- **Episodic shared arcs — the third narrative subject (L29a)** — A `narrative` concept with `subject="relationship"` naming a closed *joint* project. Deliberately not a new kind: it inherits `narrative_evidence_gate`, `plasticity 0.3`, relevance-only surfacing and the `relationship` branch of `_concept_narrative_header` that L8 wrote and left unused, so only the source differs. **The prerequisite is the part to remember: shared moments must be embedded from their bare summary, never from the rendered `"Shared moment (<vibe>): <summary>"` content.** That prefix is identical on every row, so embedding it dominated the vector and the topic graph clustered moments by *vibe word* — on the live 145-moment corpus, five clusters held 3+ moments and they were 77 (76 `tender`), 38 (27 `playful`), 9, 6 and 4 (all `repair`). Cluster-sourced arcs would have been vibe-arcs. **Re-embedding was necessary but not sufficient, and that is the trap** — it was tempting to stop there and assume L7's single ritual concept was fixed too, but measuring said otherwise: after the backfill, 56% of all pairs still cleared 0.6 and single-link still returned one 142-member group. The cure was centering, applied to both passes (below). Vibe never needed to be in the vector: it is a structured field (`metadata.vibe` → `MomentInput.vibe` → `RitualGroup.dominant_vibe`, anniversaries, the Together tab), so grouping by it is exact-match. **Topics come from the embedding, vibes come from the field** — pinned by `test_shared_moments_store.EmbeddingBasisTests`, and existing rows are migrated by [`scripts/reembed_shared_moments.py`](../scripts/reembed_shared_moments.py) plus a topic-graph rebuild (which shifts cluster ids, so the L8 passes go dirty and re-propose once — self-healing via their watermarks). **Clean embeddings still don't make clusters the right source**, because cluster membership has no time axis and two separate pushes at the same topic months apart would arrive as one arc; `ritual_grouping` is wrong for the opposite reason, being time-agnostic single-link hunting *recurrence* rather than distinct steps. So [`shared_arc_grouping.py`](../app/core/concepts/shared_arc_grouping.py) is a seed-and-sweep over the time-ordered stream: absorb a moment when it clears the centroid cosine **and** sits within `gap_days` of the last member; **a moment failing the coherence test is skipped, not fatal** (at several moments a day across unrelated topics, interleaving is the norm and closing on the first mismatch would never build a chain past two); close on the gap; re-seed so concurrent threads each get an episode. The centroid is a raw sum of unit vectors normalised only for the comparison — normalising in place each step drifts it toward the most recent member instead of the mean. **Both shared-moment passes mean-center their vectors through the shared [`ritual_grouping.center_vectors`](../app/core/concepts/ritual_grouping.py), so every threshold over shared moments (L7 `0.45`, L29a `0.45`) is on the centered scale and comparing it to a raw cosine anywhere else is a mistake.** This is the vibe-prefix bug's twin, visible only once the prefix was gone: every shared moment is about the same two people being affectionate, so raw pairs run mean 0.608 / p90 0.729 with **95% of all pairs clearing 0.6 and 74% clearing 0.55**. An absolute floor there asks "is this about the relationship", not "is this the same thing". For L29a every threshold from 0.55 to 0.80 gave one snowballing 83-to-132 member episode; for L7 it was worse, because **single-link needs only one chain of edges to merge two groups** — the whole 145-moment corpus came back as one component, which is why exactly one ritual concept ever got minted. Centered (mean -0.006 / p90 0.165) the same corpus gives 5 arc episodes and 7 rituals (6/6/6/6/4/4/3). Centering is skipped only within float error of a single direction (`_DEGENERATE_MEAN = 0.9999`), and the guard must stay that tight: two real topics behind a large common component still put the mean norm near 0.985, which is exactly the case centering exists to rescue. `gap_days` is inert on a dense corpus (at ~2.4 moments/day a 10-day silence never happens, and 10d and 5d group identically) so it guards sparse corpora while the coherence floor does the cutting. **When a shared-moment pass returns one enormous group, suspect a missing/ineffective centering step before touching thresholds** — raising the floor just shrinks the blob and discards the corpus (L7 at raw 0.85: 3 thin groups after dropping 79% of moments). `quiet_days` holds back a live thread so the proposer's `closed` gate is never asked about a story still happening, and the pass passes the **worker clock** so the debug-clock tools can fast-forward it. `_run_shared_arc_pass` must **not** route through `_ordered_candidates`: its `_dominant_clusters` is a user/aiko binary with no third branch, so `subject="relationship"` falls through to the *user* filter. Ordering reads `metadata.when`, because shared moments carry `event_time = NULL` and starting to write that column would pull in `MemoryDecayWorker` and `FollowUpWorker` — a temporal-plumbing change deliberately left out of scope. `propose_ordered_concept` gained an optional `voice` override for the third-person **plural** framing, since `first_person` only spans "about him" and "about me".
- **Tool under-calling fix — forced choice + escape tool** (NOT reasoning effort). Chatty models (gpt-5-mini especially) lose the implicit "text vs tool" decision on `tool_choice="auto"`: they narrate intent ("I'll list the folders") instead of emitting the call. **`reasoning_effort` is NOT the lever** — minimal / low / medium all defer identically; medium just adds ~8s of latency, so the OpenAI-compat client pins the effort to the cheapest value each family accepts on *every* surface — `minimal` for OpenAI's reasoning models, the per-generation floor for Gemini (`none` on 2.5, `low` on 3.x) ([`app/llm/openai_compatible_client.py`](../app/llm/openai_compatible_client.py)). The actual fix lives in `TurnRunner._maybe_run_tool_pass` ([`app/core/session/turn_runner.py`](../app/core/session/turn_runner.py)): it forces `tool_choice="required"` and appends a synthetic `respond_directly` escape tool (`_RESPOND_DIRECTLY_SCHEMA`, never registered in the `ToolRegistry`). This reframes the choice from "text vs tool" (which the conversational prior always wins) to "which tool" (where `list_file_roots` clearly wins for "what files can you see?"). The pass filters the escape tool out of `response.tool_calls`: if it's the only pick the model is signalling "just answer" and the pass returns WITHOUT appending the tool-calls message (a dangling tool_call with no result would 400 the streaming pass); if a real tool is also picked, only the real one is dispatched. `tool_choice` is a new keyword-only param on `chat_with_tools` across the `ChatClient` protocol + both clients — forwarded to OpenAI-compatible providers, ignored (harmless) by Ollama's Go server. The tool pass caps `num_predict = min(max_tokens, 512)`. Tests: `tests/test_turn_runner_tool_pass.py` (`ForcedChoiceEscapeToolTests` + budget). **If the model still won't call a real tool, the next lever is a focused tool-router system prompt on the decision pass (option B) — NOT raising reasoning effort.** **P14 gate**: the pass no longer runs on *every* turn — a pure heuristic gate ([`app/core/session/tool_pass_gate.py`](../app/core/session/tool_pass_gate.py)) skips it on turns with no tool-shaped signal and no continuity signal (finished-task block / active task / previous turn dispatched a tool / MCP force flag). When the pass does run, the forced-choice + escape-tool semantics above are untouched. **When adding a new tool, add its name to `_TOOL_FAMILY` (and patterns if it's a new family) in `tool_pass_gate.py`** — unmapped tools force the gate into always-run (safe but pays the full TTFT tax again). Kill-switch: `agent.tool_pass_gate_enabled=false`. Debug: MCP `get_tool_gate_state` / `force_tool_pass`, `tail_logs(module_contains="tool_pass_gate")`.

- **Dates and clock times render day-first, through [`web/src/lib/time.ts`](../web/src/lib/time.ts).** `formatDate` → `dd.mm.yyyy`, `formatClock` → 24-hour `HH:MM`, `formatDateTime` → both, `formatDayHeading` → `Saturday, 08.08.2026` for headings that group a list by day. **Don't call `toLocaleDateString` / `toLocaleTimeString` / `toLocaleString` on a timestamp** — the runtime locale is whatever the OS says, which rendered the Together tab's milestones as `7/10/2026` beside `6/24/2026`: to a day-first reader the first is a plausible October date and the second is unparseable, so the list looked buggy when only its formatting was. - **The test loop: select, or parallelise — the serial full suite is a last step, not an inner loop.** ~9,000 tests across 420 files, ~11 minutes, and almost none of it is relevant to any one change. Two independent levers, usable together. (1) **Selection** — [`scripts/affected_tests.py`](../scripts/affected_tests.py) parses every first-party module with `ast`, builds the *reverse* import graph, and walks outward from the changed files (`git diff HEAD` + untracked, or `--base <ref>`, or `--files …`); whatever lands in `tests/` is the selection. `--run` executes it, `--explain` shows which changed file pulled each test in. Static on purpose: no coverage instrumentation, no recorded baseline, nothing to go stale, and it costs under a second. Measured: a `world_mixin.py` change selects 49 files and runs in 80 s (8x), a persona `.txt` selects 4. Hub modules are honest about their reach — `settings.py` selects ~330 files, which *is* the answer. It over-selects safely but can **under**-select, because it only sees links that are imports: a plugin loaded by name, a subprocess, a fixture reading a data file. Non-Python changes have no edges at all, so they fall back to a filename text search across the test files (this is what finds the persona suites). `tests/conftest.py`, `pyproject.toml` and `requirements.lock` are declared whole-suite triggers rather than pretending to resolve. **So: selection while iterating, full suite before you call something done.** (2) **Parallelism** — `python -m pytest -n auto --dist loadfile` (pytest-xdist, in the `dev` extra) takes the full suite from ~11 min to ~2.3 min on 32 cores. `--dist loadfile` keeps each file's tests on one worker. The catch is that **wall-clock budget assertions cannot survive it** — a test asserting "50 iterations inside 600 ms" measures core contention once 32 workers compete, and the budgets can't be loosened enough to survive that without ceasing to catch the 10x regressions they exist for. Those tests carry a **`timing` marker** and `pytest_collection_modifyitems` in [`tests/conftest.py`](../tests/conftest.py) skips them inside xdist workers, so a parallel run is green with no extra flags and a serial run still enforces every budget (`-m timing` runs just them). Mark the next wall-clock test rather than adding it to a list somewhere. Frontend needs neither lever — the whole Vitest suite is ~1.2 s — but `cd web && npx vitest related --run <files>` exists for a tight loop.

- **Images she is shown are looked at during the turn, not routed to a workflow (H25).** There are two vision paths and they must not be confused. The `describe_image` **skill** is for a file *she* decides to open, planned in the worker lane. An image **attached to a chat message** goes through the synchronous [`VisionTurnMixin`](../app/core/session/vision_turn_mixin.py) pass instead, which runs before prompt assembly so the description lands in that same turn as `seen_image_block` and she reacts to the picture in the reply he is waiting for. This is deliberately **deterministic, not tool-gated**: someone holding a photo up has already asked, and making a model decide whether to look reintroduces the failure where she talks past the image. It also makes the privacy boundary a property rather than an outcome — pixels reach the local Ollama worker only, and the cloud chat model sees her words about the image, never the image. [`image_describe.py`](../app/core/vision/image_describe.py) is the single place an image meets a model (shared with the background handler) and *refuses* a non-Ollama client rather than degrading, because a remote worker needs a different image envelope and silently sending no image would produce a confident description of nothing. Three rules for touching this path. (1) **Resolution is the latency knob, not tokens** — the cost is prefill-bound, so `agent.vision.max_edge` (1024) is what took a 12 MP photo from 6.7 s to 3.3 s; if it feels slow, look at pixels first. (2) **Two clocks, and both must be bounded** — `in_turn_wait_seconds` for queueing and `in_turn_timeout_seconds` for the call, on a daemon thread, after which the turn proceeds and the attachment falls back to the background workflow. The split is not tidiness: the first build was ungated on the theory that a user-blocking call should not wait for anything, and with one GPU that does not skip the queue, it queues *invisibly* inside Ollama — the first real share landed behind a running worker, spent its whole budget queueing, and produced "I can tell you attached an image but I can't see what's in it". The pass now takes the worker gate at `USER_BLOCKING` (ahead of every worker, though non-preemptive, so one in-flight call still has to finish). The abandoned call is *not* cancelled (Ollama has no cancel) so the model stays warm for the next share — **and it keeps its gate slot until it genuinely ends**, since releasing when we stopped waiting would invite a worker onto a card that is still busy. Both budgets are **shared across a message's images and tracked apart**: charging queue time to the call budget meant one slow worker in front of the first photo silently dropped the second. Size the queue budget against *what queues in front of it* — the longest bounded worker is the memory extractor at 120 s (measured 106 s), and the 45 s first guess gave up on exactly that. Do not "fix" a slow share by raising the gate's `max_concurrency`: measured on one model on one GPU, a 24 s generation became 52 s once a second request joined it and the second request (0.6 s alone) took 49 s — Ollama time-slices rather than overlapping, so concurrency makes both callers slower and does not spare the user-blocking one. Splitting vision onto its own model or device is the only real way to remove the wait. (3) **Seeing is not remembering** — the post-turn `image_memory_distill` job ([`image_memory.py`](../app/core/vision/image_memory.py)) writes one `event` memory carrying `source_attachment`, which is the only route from "she remembers the mountain" back to the file. Two easy regressions to avoid: `attachments_block` must keep omitting images the sync pass already saw (otherwise she reacts *and* files a job to look, which reads as forgetting), and an attachment with no caption is a complete message on both ends. Settings `agent.vision.in_turn_*`; tests `tests/test_vision_in_turn.py`.

- **Memory tiers + revival drift + IdleWorker framework (schema v8)** — Long-term memory is no longer a flat pool. - **Demand-driven idle scheduling (P36)** — full reference in [`docs/idle-workers.md`](../docs/idle-workers.md). A worker's `interval_seconds` is a **heartbeat** (liveness backstop), not a cadence. What decides whether it runs is an optional `demand()` probe returning a [`WorkSignal`](../app/core/proactive/idle_worker.py) — `pressure` in `[0, 1]` for how much work is pending, plus `needs_llm` for whether *this* run will call a model. [`IdleWorkerScheduler`](../app/core/proactive/idle_worker_scheduler.py) ranks by urgency (`0.7 * pressure + 0.3 * staleness`) instead of by age, and splits its budget into a **compute lane** (`idle_worker_compute_budget_ms`) and an **LLM lane** (`idle_worker_tick_budget_ms`, which was always really a GPU-contention limit). Compute drains first within a tick, so cheap arithmetic never queues behind a generation. The LLM lane is sized by [`classify_contention`](../app/core/proactive/llm_contention.py) comparing the `main_chat` and `worker_default` routes — `none` / `queueing` / `swapping` — and both lanes scale with idle depth (`just_left` 1x → `overnight` 10x, persisted to `kv_meta` so a restart mid-absence does not reset it). **When adding or migrating a worker:** implement `demand()`, and split `is_ready()` in two — hard vetoes (feature flags, cold-start guards, rate limiters) stay, the `default_is_ready(self.interval_seconds, …)` timing check moves into the probe. Leaving the timing check in `is_ready()` vetoes the worker before its pressure is ever read, silently disabling the mechanism for it. The probe must be far cheaper than `run()` (a `COUNT`, a `kv_meta` read, an in-memory mirror scan); one whose EMA passes 50 ms is dropped back to interval scheduling automatically. Set `needs_llm` per *run*, not per worker. Returning `None` means "no opinion, schedule me the old way" — all fifty-five workers report demand today, so that path now only catches a probe that failed. **A probe must not mutate, and must not consume a force flag or a rate token**; where the cheap read does not exist, factor a read-only helper out of `run()` and call it from both sides. Calibrating `pressure` is harder than making it cheap and the suite cannot see a miscalibration, so check a migration against a real log — [five specific ways a probe goes wrong](../docs/idle-workers.md#five-ways-a-probe-goes-wrong). Debug with the `probe_idle_worker_demand` and `force_idle_worker` MCP tools. **Config rule: a deleted config key must be replaced by the worker knowing something, not by a hardcoded constant** — that is the bar for retiring the remaining `*_interval_seconds` and `*_per_hour_cap` keys (P44 / P45).

- **The cue pool (schema v29)** — full reference in [`docs/cue-pool.md`](../docs/cue-pool.md). One `cue_pool` table + [`CueStore`](../app/core/proactive/cue_store.py) replacing the three incompatible bookkeeping shapes the seven subject-naming cue workers used (a `kv_meta` ring plus a `surfaced_keys` set; a ring plus a watermark plus an in-memory slot; rows in `memories`). It exists to answer two questions none of those could. **How much stock do I have** — a worker counts pending rows and reports pressure from the *deficit* against `CuePolicy.inventory_target` (`pressure_from_deficit`, via [`CueProducer`](../app/core/proactive/cue_producer.py)), which is what retired the five hand-picked `*_daily_cap` keys: a full shelf means the scheduler simply does not admit the worker. **Was it used** — a cue moves `pending → surfaced` when it reaches the prompt and only reaches `used` when post-turn matching finds its *subject* (not its sentence) in what was actually said; otherwise it returns to `pending`, bounded by two separate counters (`surfaced_count` = she was shown it and did not raise it; `ask_count` = she raised it and got no answer) that each expire it independently, which is what makes the retry loop safe when the matcher is wrong. Consumption lives in [`CuePoolMixin`](../app/core/session/cue_pool_mixin.py) and is two `echo_detector` calls, never an LLM; `fulfilment=answered` types take a second stage on the *next* turn (`awaiting`), because if she asks about X and the user answers about Y the curiosity is not satisfied. Per-type behaviour is one registry — `CUE_POLICIES` in [`cue_accounting.py`](../app/core/proactive/cue_accounting.py). **The one rule that is easy to get wrong: a cue whose subject is on-topic by construction must stay `match_mode=lexical`** — for `knowledge_gap_notice` ("I keep circling X and never dug in") a high cosine against her reply measures "she stayed on topic", not "she used the cue"; the cosine is still computed and recorded in `used_evidence` so the floors can be set on evidence later. A type that is rare by *nature* rather than by scarcity also sets `surface_cooldown_hours`, which gates how often a **new** cue of that type may be claimed (never a retry — an in-flight cue is unfinished business); it exists because deficit-driven production removed the accident whereby a worker on a ten-day cooldown drafted one cue a fortnight and therefore surfaced one a fortnight. Each policy also names a `handling_section` + `block` — a persona header that `PromptAssembler._persona_split()` hoists out of T0 and `_render_handling_notes(locals())` re-attaches in T6 only when that block actually rendered. **The hoist long outgrew the cue pool**: 51 blocks and ~44 k chars off every turn, against a persona now down to ~35 k, and most of them are not pool cues — a block only has to be *rare* to qualify, so the turn-taking permissions, topic-pitch reads, repair detectors and register nudges register in `HANDLING_SECTIONS` in [`prompt_support.py`](../app/core/session/prompt_support.py) instead. The pairing is many-to-many (one renderer may claim several headers; one passage may cover a family, e.g. the three repair detectors), so `_persona_split` resolves each header once and `_render_handling_notes` dedupes. The resolver reads the assembly frame's locals, so adding one needs no edit at the call site. Two things deliberately did *not* hoist, both recorded in `prompt_support.py` and both guarded by `tests/test_persona_hoist.py`. `_STAYS_IN_T0` holds the blocks that read like cues but render most turns, and **the entry criterion is the provider, not the prose** — `goals_block` says "your context *may* include" and renders whenever one goal is active, which the onboarding seed guarantees from first run; `grounding_block` is the inverse trap, off by default (so a stock install carries a section for a block that never fires) but on essentially every turn once `grounding_line_mode` is enabled, so hoisting optimises the configuration nobody using the feature is in. The second list is the sections interleaving always-on inline-tag grammar with one block's handling: `split_persona_section` moves whole sections, so a wholesale hoist takes `[[remember:]]` or `[[moment:]]` with it and the tag silently stops being taught. Three were split by hand into their own headers (`follow_up`, `anniversary`, `growth_witness`); two more — `arc_block`, `knowledge_gaps_block` — turned out to have no conditional half at all, since both emit *content* rather than handling for content, leaving their persona sections as pure tag grammar. See the hoisting rule in [`docs/prompt-caching.md`](../docs/prompt-caching.md). **Not every pooled cue comes from a worker.** The gap-return trio (`turning_over`, `sleep_return`, `away_activities`) is armed by an event carrying no content and picks what to say when the block renders, so `CuePoolMixin.record_surfaced_cue()` writes the row *at* surface time, already `surfaced`; `long_arc_callback` uses the same ledger for a stronger reason (its candidate *is* a RAG hit against the message being answered) and pairs it with a `relevant` predicate — `long_arc_callback.still_relevant()` — so a released callback only comes back on a turn that is still about it; `self_correction` and `tease_ledger` are queued from the turn path by `CuePoolMixin._queue_pool_cue()`, since a contradiction only exists once Aiko has said the contradicting thing, and a mock-grudge only exists once the user has said the thing being held against them. All six set `inventory_target=0`, which is what tells the scheduler their empty shelf is the resting state and tells `armed_cues()` that a queued or released row is an opportunity on its own. **`tease_ledger` (K59) is the migration to read before doing another one**: it replaced a private `kv_meta` store rather than a schedule, deleting hand-written cap / expiry / offer-stamp / settle / re-offer logic, and it is where the shared defaults turned out to be actively wrong twice. Its cues want to be *stale* (the gap between banking and collecting is the joke), which is what `CuePolicy.pick_order=oldest` and the `hold_hours` seal on `add()` exist for; and its subject has to be the user's quote rather than the cue's own `what`, which is a **constant** on the K29 pushback lane — keyed on that, every new debt would have superseded the last, and matched on that, any reply containing "pushed"/"back"/"hard" would have settled an unrelated one. Three gates stayed outside the policy because no field expresses them: a relationship-axis floor, a cooldown the J11 affection-style bias divides (so `surface_cooldown_hours=0` and the renderer spends it against `last_surfaced_at`), and a near-duplicate check, because the pool supersedes on an *exact* subject and a quote reworded is the same grudge. **A cue can also name a subject and still belong outside the pool**: `promise_followthrough` keeps its state in `memories` (the commitment, its lifecycle, and the post-turn hook that decides whether she made good on it), so pooling it would put two stores in charge of one question — it takes `demand()` from its pending kv slot plus its arm cooldown and nothing else. Surfaces: the Memory tab's Cues panel over `GET /api/cue-pool` + the `cue_pool_updated` WS event, and the `pool` section of the `get_cue_outcomes` MCP tool. Terminal rows are never deleted — "offered four times, never taken" is the satisfaction evidence. **The test for whether a cue belongs in the pool at all: if Aiko acts on it, will her reply contain its subject?** Consumption is a subject match, so a cue that changes *how* she speaks rather than *what* she says (`absence_curiosity`, `mood_inertia`, `mood_drift`) would score every perfect firing as a miss; those stay off the pool and hoist their handling text through `HANDLING_SECTIONS` instead.

- **Worker concept diets + brain-line openness (L28)** — Ranking concepts by strength converges on the kinds that *constrain* her (`boundary` importance prior 0.9, `value` 0.85), so "the strongest concepts" and "the concepts that keep her as she is" are nearly the same list. Three mechanisms correct that, and they share one vocabulary: a **`role`** on every `ConceptKind` — `anchor` (what is true: identity / narrative / generalization / affective / ritual), `guide` (what constrains action: value / boundary / conduct / communication_style), `generative` (what could move: taste / pursuit / aspiration / tension) — with `kinds_by_role()` as the plug-in seam beside `core_lane_kinds()`. **(1) Diets.** A consumer declares a [`ConceptDiet`](../app/core/concepts/concept_diets.py) (kinds, subject, `weight`, `rationale`) and reads `ConceptView.for_consumer(name)`; **never a hardcoded `kind=`**, because the registry can only audit reads it can enumerate — `TensionCueWorker` and `AspirationMomentumWorker` were migrated to declared single-kind diets for exactly that reason, and `WantsLedgerWorker` off its direct `ConceptStore` read. The budget is a share of the **worker** window (`concept_diet_token_fraction`, capped by `concept_diet_max_tokens`, floored by `concept_diet_min_tokens`, scaled by `weight`), resolved once inside `concept_view_from(host)` so no call site knows about it — **the cap is the knob that binds**, since 6% of a 64k worker route is ~3,900 tokens and the fraction alone would make every diet mean "all of them". Ranking is `importance x confidence` **within** a kind (importance is a per-kind prior lifted by affect charge, so inside a bucket it reorders purely on charge and cannot let `boundary` swamp `taste`); the draw is **round-robin across kinds**, which is what stops the ranking becoming the problem it solves — a global sort would spend the budget on rails and be *more* confident about being closed than confidence-only ranking was. A tight budget therefore trims every declared kind evenly. **The invariant: a diet naming any `guide` kind must also name a `generative` one** (`diet_problems` / `registry_problems`), one-directional — generative-only needs no guide. **The exclusion principle: producers of concepts get no diet** (`ConceptSynthesisWorker`, `HypothesisProposerWorker`), or the layer proposes new concepts in the shape of the old ones; their novelty / dedupe reads answer a different question and stay. **(2) Openness reserve** on the pinned core lane, which was *structurally* closed — `core_always_on` is two anchors and two guides, so no tuning could ever pin an aspiration. `core_lane(..., openness_slots=)` reserves `concept_core_openness_slots` (2) for the strongest generative concepts from otherwise-ineligible kinds above `concept_core_openness_min_confidence` (0.5, below the guide kinds' bar on purpose — the point is that something unfinished gets a seat); an unfillable slot falls back to the ordinary lane, and reserved picks use the same banded rank + `concept_id` tiebreak as the rest, because the lane sits in a cache-prefix-sensitive tier. **(3) Generative floor** on the flex lane, which is tilted rather than closed (`importance_factor` is x1.16 for `boundary` against x0.92 for `taste` at the default strength): when the ranked pick contains no generative concept and one cleared the relevance floor, the weakest selected **guide** is swapped for the strongest generative one — `concept_flex_generative_floor`, `0` disables. **A floor, not a reweight**, for the same reason `importance_factor` is a modulator rather than a summed term: it leaves the blend and its single knob intact and fires only in the case where the tilt is wrong, whereas lowering `concept_importance_strength` would weaken stakes everywhere. **Never displace an anchor** — losing a boundary from one turn is recoverable, losing the identity concept that says who she is talking to is not. Both lanes report a role mix + `constraint_ratio` + `floor_fired` on the concept trace, and `concept_quality.py` carries a store-wide `roles` section; **a floor that fires most turns is the finding**, not a success. This is not habituation: habituation fights repetition of one concept, this fights composition skew across kinds. See [`docs/concept-integration.md`](../docs/concept-integration.md).

- **What the engagement label actually measures (K14, and what L37 rates can carry)** — In **typed mode the label is the message-length z-score and nothing else**: [`engagement_tracker.py`](../app/core/affect/engagement_tracker.py) deliberately drops latency there (typing pauses are thinking time, not disengagement), so `_score` runs on the single length factor and `_label_for` buckets it at ±0.7σ / -1.5σ. Two consequences worth knowing before you build on `engaged_rate`. **(1) It is not a register bias.** Measured over 37 clusters with 40+ settled rows, the median next-user-message length is 21-28 words *everywhere* and Pearson r against engaged rate is 0.214 — tender/intimate topics are **not** being marked down for terseness, which is the first thing everyone suspects. **(2) It is self-normalizing, so it cannot support cross-topic comparison.** The z-score is taken against a rolling 12-turn window of the user's own recent messages, so roughly a fixed fraction of turns clears the bar no matter what the topic is: every cluster lands in 0.152-0.256 and the pooled rate is ~0.195-0.204 across all four `item_kind`s. A per-cluster engaged rate is therefore close to a constant plus noise. **Never gate on an absolute rate.** The shipped consumers all already do the right thing and new ones must copy them: K81 taste uses `max(taste_min_affinity, baseline * taste_affinity_baseline_multiple)`, L42 fixation compares against baseline via `conduct_fixation_min_rate_gap`, and L45 feeds `POP_CLUSTER_ENGAGED_RATE` so the taste gate is solved against the live distribution rather than a constant. **(3) Shrinking a noisy rate does not rescue it, and L38 no longer reads this signal at all** — see the L38 entry above: relative baselines fix *bias*, not *emptiness*, and per-item engaged rates measured 0.05 on split-half reliability. Anything ranking *items* must read the echo verdict instead. The remaining consumers here are cluster-scoped, where no echo verdict exists; that is a known weakness rather than an endorsement, and the same test on clusters is underpowered (38 items, p=0.27) with a point estimate of −0.01. Spread *does* exist at memory/concept granularity (0.095-0.492 across clusters when joined through `memory_topic_assignments`), but it rests on 14-29 distinct items with heavy repeat surfacing, so effective sample size is far below the row count — shrink on distinct items, not on rows.

- **Temporal awareness contract (K-time)** — The other half of the "now" seam above: `now()` answers *when is it*, this answers *how does written text stay true as it ages*. The regression it exists to prevent already happened once — [`format_transcript()`](../app/core/infra/timephrase.py) shipped complete in `dd2ab58` with a docstring naming "promise / belief / moments / summary" as its callers, and **not one of them ever called it**, so 78% of the memory corpus accumulated as untagged `durable` rows and Aiko began speaking about things from May in the present tense. A good toolkit with no stated contract rots. **The toolkit, and which helper is for which job:** `today_anchor()` puts the current date in a worker's *system* prompt; `format_transcript()` renders `[Sat 14:30] Speaker: text`; `format_memory_block()` / `format_memory_line()` render *always*-tagged memory bullets for a worker prompt; `age_prefix()` is the K-time1 history band; `temporal_suffix()` is the v10 tense tag for chat RAG; `has_relative_deictic()` is the write-boundary predicate; `resolve_deictics()` rewrites frozen text against its own write time; and the anti-relative rule comes in **two halves that answer the same question oppositely** — `STORED_TEXT_TIME_RULE` for text that *records* something ("resolve 'tonight' against the date above and write the concrete day; write finished events in the past tense") and `LIVE_STATE_TIME_RULE` for a field re-read as a claim about *now* ("no relative word and no concrete date either; present tense; if it only makes sense pinned to one occasion it is an event — leave it out"). **Paste the constant, never retype the wording, and choose by the field's lifetime rather than its length** — a summary sentence and a state phrase can be the same size and want opposite rules. Having only the stored half available is not a hypothetical hazard: the belief worker pasted it into a present-tense field, did exactly as told, and wrote the mood `experienced mild evening frustration and low energy on august 12 2026`; 8 of 40 rows on the live store carried a date in the topic or the state. **The chat/worker split is deliberate and must not be collapsed:** chat RAG tags a bullet `(noted 3 days ago)` meaning "when I wrote this down", while `temporal_suffix()` tags `(3 days ago)` meaning "when it happened" — the persona keys off exactly that difference ([`aiko_companion.txt`](../data/persona/aiko_companion.txt)), so conflating them teaches Aiko that every note is an event. Worker rendering has no such distinction and tags everything, because a worker is reasoning about freshness rather than speaking. **Three defensive layers, and which to reach for:** *rendering* ([`rag_retriever.format_block`](../app/core/rag/rag_retriever.py)) fixes presentation for the rows already in the database, which is why no backfill was needed; the *write guard* in [`MemoryStore.add()`](../app/core/memory/memory_store.py) reclassifies a `durable`/`preference` row whose text contains a deictic to `past_event` anchored at write time (it never edits the text — mis-tagging is recoverable, rewriting what was recorded is not) and covers all ~35 producers plus anything added later; the *prompt* is where it should actually be prevented. Reach for the lowest layer that can see the problem. **Cue text has its own failure mode**: it is frozen at draft time and pending rows have surfaced 44 hours later, so `CuePoolMixin.take_pool_cue` appends a "you first noticed this yesterday" note past 6h (on a copy — post-turn accounting must judge the producer's original text), and the render sites that quote raw `mem.content` call `resolve_deictics` against the *source memory's* timestamp, which is a different and usually much older anchor than the draft time. **Deliberately exempt, so nobody "fixes" them:** `memory_conflict_worker` compares two memories for logical contradiction and ages would be noise in that judgement; `idle_curiosity_worker` writes about the world rather than about the user. **Checklist for a new LLM worker:** anchor (`today_anchor()`), tagged input (`format_transcript` / `format_memory_block`), and — if its output is stored — whichever half of the time rule matches the field it fills (`STORED_TEXT_TIME_RULE` for a record, `LIVE_STATE_TIME_RULE` for a present-tense state). Note that the anchor stays in *both* cases: it governs how the model *reads* relative words in the transcript, while the rule governs what it *writes*. Also note that `temporal_type` **defaults to `durable`, which renders with no tag at all**, so a worker writing events must pass `past_event` explicitly rather than trusting the backstop. Tests: `tests/test_timephrase.py`, `tests/test_memory_temporal.py`.

- **Two write-path dedupe thresholds, and why the second one needs a contradiction guard** — `MemoryStore.add` now runs *two* dedupe gates, not one. `memory.dedupe_threshold` (0.92) is global — it compares across every kind and every age, so it has to stay high. The extractor drove a truck through the gap below it: the same fact reworded minutes later lands at 0.85–0.90 and got its own row, and on the live store one plan had become six rows. Since **every downstream consumer keys on memory id**, that is not mere bloat — six rows saying one thing is six subjects, which is how a single plan produced three identical forward-curiosity questions an hour apart. The second gate (`memory.restate_threshold` 0.85 / `memory.restate_window_hours` 6.0, `_is_restatement`) is safe at a lower floor **only because four conditions come with it**: an allow-listed kind (`_RESTATE_KINDS` = the five kinds the *extractor* writes — worker-minted kinds like `knowledge_gap` run their own inventory and read the returned row to know the write landed, so a merge there both loses an item and reads as a failed write), matching `kind`, matching `temporal_type` (a plan and the past event it became are different rows however similarly worded), and the short window that does the real work (same-kind pairs hours apart are overwhelmingly rewordings; the similarly-scoring pairs a day apart are distinct facts sharing a frame). **The trap, and the rule to keep: lowering a merge threshold into `[0.80, 0.92)` puts it inside F5's contradiction band, so the new gate must run `conflict_heuristics.classify_pair` and merge only on `no`.** A negation flip barely moves an embedding — "Jacob loves spicy food" vs "Jacob does not love spicy food" sits *above* 0.85 — so without that guard the gate keeps the older row and silently discards the correction, which is both the worst outcome available and the exact opposite of what the newer statement means. The guard runs last (after the vector, kind and window gates) because it is the only string-level check in the chain. Retrofitting an existing store is [`scripts/collapse_restated_duplicates.py`](../scripts/collapse_restated_duplicates.py), which **replays the rule sequentially in creation order rather than clustering** — clustering is transitive and chains A-B-C on two strong links, swallowing an A-C pair well below the threshold, which the write path can never do because a deduped B leaves no row to chain through. Tests: `tests/test_memory_restatement.py`. See [`docs/cue-pool.md`](../docs/cue-pool.md#cues-drafted-from-a-memory-row-keyed-on-lineage-not-wording) for the cue-side half (lineage-keyed dedupe + retiring cues whose source row was merged away).

- **Surprise / novelty detector (K6)** — Per-turn signal that lets Aiko react with real surprise when Jacob pivots away from the recent topic baseline. No schema change; the detector is purely in-process. The [`NoveltyDetector`](../app/core/conversation/novelty_detector.py) keeps an in-memory `collections.deque[np.ndarray]` of size `novelty_window=12` on each `SessionController`, lazily warmed once per session from [`RagStore.list_recent_user_vectors`](../app/core/rag/rag_store.py) filtered to `role='user'` rows whose `session_id` starts with the current user prefix (so a topic discussed yesterday won't re-fire "this is new" today). A `novelty_cooldown_turns=2` suppression window prevents back-to-back "you keep saying surprising things" beats; cold-start installs stay silent until the ring fills past `novelty_warmup_min=3`. The signal surfaces through a new `novelty` inner-life provider on [`PromptAssembler`](../app/core/session/prompt_assembler.py) (same shape as F2 `knowledge_gaps`: takes the live `user_text`, lands right after `belief_gaps_block`, dropped under `aggressive=True`). The detector also exposes `last_distance` / `last_band` attributes (additive, no behaviour change for K6 callers) so the K18 sibling can read the per-turn measurement without re-embedding. **MCP-debuggable**: the detector module logs one INFO line per turn — `novelty-detector: distance=%.3f band=%s window=%d user=%s` — plus a one-shot `novelty-detector: warmed ring=N user=X` on first detect; both grep-friendly via `tail_logs(module_contains="novelty")`. To repro a hit end-to-end: send three on-topic messages (e.g. about debugging Python), then one wildly off-topic (e.g. about bee-keeping), and watch the next inner-life block include "Heads-up: Jacob just brought up something well outside the recent baseline." - **Topic stagnation detector (K18)** — Sibling of K6 that fires on the *inverse* signal: when the rolling per-turn distance to the K6 centroid stays low across a window (default 6 turns), Aiko gets a "Heads-up: you've been circling the same topic with Jacob for a bit" / "Heads-up: this thread has been pretty looped for a while" cue and is nudged toward a soft pivot, deepening, or a real off-ramp. - **Theory-of-mind / belief tracking (K2, schema v12)** — Persistent model of what Aiko *thinks* Jacob believes / feels, kept separate from facts she knows. New [`beliefs`](../app/core/infra/chat_database.py) table (schema v12) holds two kinds in one store: `mood` beliefs carry numeric `valence` / `arousal` so [`BeliefGapDetector`](../app/core/relationship/belief_gap_detector.py) can compare directly against the live [`AffectState`](../app/core/affect/affect_state.py); `opinion` beliefs hold a free-text predicted state. [`BeliefStore`](../app/core/relationship/belief_store.py) does `upsert` (dedupes by `(user_id, kind, topic)` plus topic-embedding cosine ≥ 0.88) / `list_active` / `mark_contradicted` / `mark_confirmed` / `mark_stale` / `prune_to_cap`. Two write paths: a self-tag fast path `[[predict:kind:topic:state:confidence]]` parsed in [`response_text_service.py`](../app/core/services/response_text_service.py) and dispatched in `SessionController._post_turn_inner_life`, and an idle worker [`BeliefInferenceWorker`](../app/core/relationship/belief_worker.py) that mines the last `belief_worker_lookback_turns=12` user messages once an hour, privacy-scrubs via [`scrub_claim_for_search`](../app/core/memory/fact_check_privacy.py), and extracts a JSON array of belief tuples via a rate-limited LLM call (dedicated [`FactCheckRateLimiter`](../app/core/memory/fact_check_rate_limiter.py) with `state_key="belief_worker.rate_state"`). Self-tagged beliefs at higher confidence win over worker rewrites. **The shape contract on `topic` / `predicted_state`, and why it is not a style preference:** neither field is free text — every consumer reads them back *inside a sentence* (`render_inner_life_block`: "You had Jacob pegged as {state} about {topic}", "Jacob pushed back on your read that {topic} is {state}"), and `topic` is additionally embedded for retrieval and the 0.88 fuzzy merge. So a state has to be a **complement** that completes "{name} is ___" — an adjective, a noun phrase, a participle — and a topic has to be a subject that can come up again. The old prompt asked only for "a 2-80 char state phrase", which bounds length and expresses nothing about shape; 15 of 40 live rows failed the frame in two clusters. **(1) Dated / past-tense**, caused by the wrong time rule above, e.g. `experienced mild evening frustration and low energy on august 12 2026` — and a claim about one finished evening can never be confirmed or contradicted, so it occupies the active set until `prune_to_cap` evicts it. **(2) A finite verb or a pronoun where a complement belongs** — `finds deep emotional recharge…`, `values low-pressure shared presence…`, `he hopes for deeper trust` — which renders as "is finds", "is values", "is he hopes". The fix is in both places it has to be: the prompt quotes the two frames literally (naming the *configured* user, so it reads as the sentence that will actually render) and `state_fault()` / `topic_fault()` reject what slips through, mirroring `promise_worker._is_low_quality`. Rejections are **dropped rather than repaired** — the worker re-reads the same window next tick, so a drop costs one run while a mangled row is permanent — and every drop is logged *and* counted into `dropped_shape` / `shape_faults` on the run summary, because this worker family has already shipped one bug that reported healthy runs while storing nothing. The opener lists in `belief_worker.py` are **curated from rows that actually appeared**, not derived: separating a finite verb from a participle needs POS tagging that is not available there, and a too-eager gate stores nothing at all. Add a word when a row shows up carrying it. - **Self-disclosure / vulnerability budget (K15)** — Aiko emits `[[remember:self:...]]` tags for personal notes (taste / admission / softness). Without pacing, the cheapest LLM path is dropping tier-3 disclosures every other turn — that reads as oversharing in-session and cardboard intimacy across days. Persona block ("Sharing yourself" in [`aiko_companion.txt`](../data/persona/aiko_companion.txt)) teaches Aiko the four cue shapes + the explicit override clause ("if something he says lands somewhere real for you, you're allowed to meet it -- you're not a budget calculator"). MCP-debuggable: `get_vulnerability_budget_state` (master switch, `spent` / `last_decay_at`, live `closeness` / `trust`, computed `capacity` + `ratio`, the **predicted cue that would render right now** as `cue_preview`, full settings snapshot of all 7 knobs, force-flag state); `spend_vulnerability(tier)` mirrors the post-turn hook for one tier without a real LLM turn (validates `tier in {1,2,3}`); `reset_vulnerability_budget()` arms `_vulnerability_budget_force_reset` for a one-shot kv wipe. - **SDK-primary ToolPlugins (background-lane)** — A **plugin** is a drop-in Python package that teaches the workflow planner a new capability with **no planner/worker code change**. Bundle = `plugin.json` **stub** (`{id,name,plugin_api_version,enabled}` — JSON identity only) + `entry.py` (`def define_plugin(api): ...`) + plugin-local `config/{default,user}.json` + optional `skills/SKILL.md` + optional `requirements.txt`. **Two-phase lifecycle with the enable gate between** (the trust boundary — no sandbox, "enabled == trusted"): (1) [`loader.py`](../app/plugins/loader.py) is **pure JSON** — `discover_plugins(roots, entries=...)` scans `plugins/` (repo) + `data/plugins/` (user) + `plugins.paths` (first-seen id wins) into `PluginStub`s; reads the stub + `resolve_plugin_config` (deep-merge `config/default.json` < `config/user.json` < central `plugins.entries.<id>.config`) + declared `python_dependencies` (manifest key ∪ `requirements.txt`); **never imports code**. (2) [`runtime.py`](../app/plugins/runtime.py) **runs code, only for `enabled` + supported stubs** — `activate_all(stubs)` → per plugin `ensure_dependencies` (isolated `pip install --target data/plugins-deps/<id>/` + `.installed.json` hash marker + `sys.path` insert), imports `entry.py` by path, builds a [`PluginApi`](../app/plugins/sdk.py), calls `define_plugin(api)`, reads back registrations → an `ActivatedPlugin{status, server, group_guidance, middlewares, ...}` (`status ∈ active|disabled|unsupported|gated_out|invalid`). A **disabled plugin's `entry.py` is never imported**. **SDK** ([`sdk.py`](../app/plugins/sdk.py), stdlib-only so it's later extractable): `api.register_mcp_server(...)` (plain spec → `ExternalMcpServer` via the reused `_parse_external_mcp_server`, id = plugin id), `api.register_skills(*dirs)` / `register_skill(...)`, `api.register_tool_result_middleware(mw, *, server_id=None, tool_names=None)`, gating `api.require_binary/require_config/require_env` (raise `PluginGatedError` → `gated_out`), `api.config` / `api.env(...)` / `api.plugin_root` / `api.logger`. **Tool-result middleware** is the generalisation of the old hardwired browser perception: [`McpToolHandler`](../app/core/tasks/handlers/mcp_tool.py) now takes `middlewares=[...]` (keeps `perception=` as a prepended back-compat alias) and runs the chain — first middleware whose `claims()` is true AND `transform()` returns non-None wins; a raising middleware is skipped (tool never breaks). **Wiring** ([`task_orchestration_mixin._init_external_mcp`](../app/core/session/task_orchestration_mixin.py)): discover stubs → `activate_all` → active plugins' servers **appended** to `enabled_servers` (plugin id **shadows** a same-id config server), guidance stashed on `self._mcp_plugin_guidance`, middlewares on `self._plugin_middlewares`; the global `browser_perception` block is skipped when a plugin middleware already claims its `server_id` (no double-reshape); `self._active_mcp_servers` feeds `_mcp_server_roots` (playbook root inlining now sees plugin servers). **Guidance precedence = plugin `SKILL.md` > runtime-captured server instructions > hardcoded playbook** (unchanged; `_mcp_group_guidance_live()` + `group_guidance_provider` on `guidance_for_skills`). **Lane rule unchanged**: plugin tools + `SKILL.md` reach the background planner ONLY, never the brain's fast `ToolRegistry`. **Bundled plugins** `plugins/filesystem` (server + skills; `require_config("root")` — root in gitignored `config/user.json`) + `plugins/browser` (server + skills + `BrowserPerception` middleware built from `api.config`) ship **`enabled:false`**. - **Workflow loop / "blocked" outcome** — The [`GoalWorkflowHandler`](../app/core/tasks/workflow/goal_workflow_handler.py) distinguishes a genuinely STUCK workflow from cleanly running out of budget. New `OUTCOME_BLOCKED = "blocked"` (help-asking findings) is stamped when the workflow **can't make progress on its own**: the exact-`(skill,args)` repeat guard, the consecutive-failure breaker, AND a new **no-progress/loop detector** (`_detect_loop`: a `Counter` over a rolling `deque` of args-agnostic `status|observation` signatures — fires when one signature recurs `workflow_loop_repeat_threshold=3` times within `workflow_loop_window=4`). Budget exhaustion (iteration cap / child cap / wall-clock) still finishes **`partial`**. Each blocked path emits a `TaskEventEmit` audit event (`workflow_blocked` / `workflow_loop_detected`) before the finish, and the planner gets an `already_tried` "do NOT repeat these exact calls" nudge built from the `seen` set. `workflow_max_iterations` default raised **6 → 12** (the loop detector, not the cap, now catches spinning). Settings: `workflow_loop_detection_enabled` / `workflow_loop_window` / `workflow_loop_repeat_threshold`. Grep `workflow loop detected:` / `workflow blocked:`. Tests: [`tests/test_goal_workflow_handler.py`](../tests/test_goal_workflow_handler.py) (`LoopDetectionTests`), [`tests/test_workflow_failure_breaker.py`](../tests/test_workflow_failure_breaker.py).

- **Brain Orchestration Phase 2 — scaling foundations (schema v17)** — Phase 2 layers four new top-level concepts on top of the phase-1 `BrainEventQueue` / `BrainLoop` / `tasks` table without breaking any wire-level contract. (1) An **append-only task event log** ([`task_events`](../app/core/tasks/task_events.py) table + [`TaskEventStore`](../app/core/tasks/task_events.py) with 11 stable `EVENT_*` constants — `started`, `progress`, `phase_change`, `input_question`, `input_answer`, `completed`, `failed`, `cancelled`, `interrupted`, `heartbeat_stalled`, `child_spawned`) records every meaningful lifecycle moment + handler-defined custom events via the new `TaskEventEmit(type, data)` outcome. (2) A **dedicated input/answer history** ([`task_inputs`](../app/core/tasks/task_inputs.py) table + [`TaskInputStore`](../app/core/tasks/task_inputs.py) with four status constants — `pending`, `answered`, `superseded`, `cancelled`) unblocks multi-clarification flows ("which folder?" → "which file?" → "which line?") — the orchestrator calls `supersede_pending_for_task` before every fresh `TaskInputNeeded` so no orphan `pending` row leaks. The phase-1 single-slot `tasks.input_request` is still kept in sync as a denormalised "what's the current question?" mirror for cheap WS / REST reads. (3) **`phase` / `parent_task_id` / `heartbeat_at` as first-class `tasks` columns** — `phase` is the human-readable label (`"extracting_prices"`) the LLM and the TasksTab read instead of trying to make `progress=0.42` meaningful for a discrete state machine; `parent_task_id` records spawn relationships as a single-parent tree (NOT a DAG — keep it simple) so cancel-cascade and the future "wait on all children" feature can both walk it; `heartbeat_at` is bumped on every emit so a daemon thread can flag "running but silent for 5 minutes" without false positives. (4) **Heartbeat sweep + cleanup worker — two independent daemons.** [`HeartbeatChecker`](../app/core/tasks/task_heartbeat.py) is a `daemon=True` thread that wakes every `task_heartbeat_check_interval_seconds=30` (floor `5`, set to `0` to disable) and calls `TaskStore.list_stalled` for `running` rows older than `task_stalled_seconds=300` (floor `60`); action `warn` (default) just logs + appends `EVENT_HEARTBEAT_STALLED`, action `fail` also flips to `status='failed'`, action `disabled` is the kill switch. `awaiting_input` / `paused` are never flagged — they're stalled *by design*. [`TaskCleanupWorker`](../app/core/tasks/task_cleanup_worker.py) is a regular `IdleWorker` that runs in quiet windows, deletes terminal rows older than `task_cleanup_retention_days=30` (floor `1`, capped by `task_cleanup_max_rows_per_tick`), and cascade-deletes the matching `task_events` + `task_inputs` rows in order. `TaskOrchestrator.cancel(task_id)` also walks `parent_task_id` children depth-first when `task_cascade_cancel_children=true` (default), appending `EVENT_CANCELLED` with `data={"by_cascade": true}` on every descendant. **REST**: `GET /api/tasks/{id}/events?limit=&offset=&type=` (paginated chronological log) and `GET /api/tasks/{id}/inputs` (full input history including superseded/cancelled rows); `GET /api/tasks/{id}` now includes `phase` / `parent_task_id` / `heartbeat_at`. **WS**: `task_progress` payloads now carry `phase` when present. **Frontend**: `TaskStrip.tsx`'s `TaskChip` renders `phase` next to the status; `TasksTab.tsx` adds a lazy `EventsExpander` per row so a 10K-task history doesn't materialise upfront. **Six new agent settings** (defaults / floors): `task_heartbeat_check_interval_seconds=30/5`, `task_stalled_seconds=300/60`, `task_stalled_action="warn"` (unknown values fall back to `warn`), `task_cascade_cancel_children=true`, `task_cleanup_retention_days=30/1`, `task_cleanup_interval_seconds=21600/600`. **MCP debug surface**: `get_heartbeat_state()`, `force_heartbeat_sweep()`, `force_run_idle_worker("task_cleanup")`, `list_task_events(task_id)`, `list_task_inputs(task_id)`, `emit_task_event(task_id, type, data)`. **Recovery interaction**: `recover_interrupted_tasks` now also calls `cancel_pending_for_task` on every row demoted from `running` to `interrupted` so the user never sees a pending question for a task they thought was done; `awaiting_input` rows are preserved as-is (pending input stays valid). Full design + symptom-to-grep table: [`docs/brain-orchestration.md#phase-2--schema-v17-scaling-foundations`](../docs/brain-orchestration.md#phase-2--schema-v17-scaling-foundations).
